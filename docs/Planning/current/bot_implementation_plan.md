# Bot Implementation Plan

Поэтапная реализация бота с нуля.

**Основа:**

* [bot_architecture.md](bot_architecture.md) — архитектура (компоненты, pipeline, сущности)
* [bot universal algorithm brainstrom.md](bot%20universal%20algorithm%20brainstrom.md) — decision loop
* [bot concept brainstrom](bot%20concept%20brainstrom) — доменные детали

**Подход:** код бота пишется поэтапно. Каждый этап — рабочий бот с ограниченным
функционалом. Следующий этап добавляет возможности поверх предыдущего.

**Папка нового бота:** `Assets/Scripts/BotV2/`

Старый код (`Assets/Scripts/Bot/`) остаётся как справочник. Оттуда можно копировать
проверенные фрагменты (collision utils, timing, snapshot builder logic).

## Этапы

### Общее правило для этапов 1–4

* Все тестовые ситуации требуют только один шаг.
* Построение цепочек не используется.
* Бот работает по pipeline одного шага:
  `Trigger → Snapshot → Classify → ActionGenerator → ActionSelector → StepExecutor`
* **Безопасность** на этапах 1–8 — это безопасность самого шага в окне его исполнения.
  Если после безопасного шага впереди остаются угрозы, они обрабатываются
  следующим пересчётом, а не делают текущий шаг unsafe.

### Этап 1. Один объект, один простой тип угрозы — ✅ ВЫПОЛНЕН

* Обрабатывается только `Threat`.
* На экране один объект.
* Один простой тип угрозы (`smallNotAliveRoad`).
* Бот строит один шаг.
* Проверяется корректность выбора безопасного действия.

### Этап 2. Один объект, все типы угроз — ✅ ВЫПОЛНЕН

* Все типы `Threat` (`smallNotAliveRoad`, `smallNotAliveRoadAndRoof`, `bigNotAlive`, `mediumNotAlive`, `bigAlive`).
* На экране один объект.
* Если безопасных действий несколько — выбор по энергоэффективности.

### Этап 3. Один объект, все категории — ✅ ВЫПОЛНЕН

* `Threat`, `Target`, `Collectible`.
* На экране один объект.
* Выбор по приоритетам: безопасность → профит → энергия.
* Реализовано: DecisionRank (LifeCollectible > Target > OtherCollectible > ThreatSafety),
  ProfitScore, smallAlive как Target, сбор коллектиблов через SwitchLane.

### Этап 4. Несколько объектов, один шаг — ✅ ВЫПОЛНЕН

* На экране несколько объектов, но ситуация решается одним решением.
* Бот определяет ближайший релевантный объект.
* Строит один безопасный шаг с учётом остальных видимых объектов.
* Остальные объекты используются для оценки immediate safety шага и того,
  что останется после пересчёта, но не требуют построения цепочки.

#### Ограничения для Stage 4 паттернов

* Паттерн не должен требовать прогноз на 2+ шага для выживания.
* В каждом тестовом кластере должен существовать хотя бы один безопасный one-step выбор.
* Не допускать физического наложения `Target` и `Threat` в одной линии (например, `smallAlive` поверх `mediumNotAlive`).
* Если `Collectible` расположен сразу за `mediumNotAlive`, сценарий считается корректным только если сбор возможен без потери жизни в пределах одного шага.
* Dense-паттерны допустимы, но без "безвыходных" конфигураций, где любой one-step приводит к урону.

#### Тестовые паттерны, на которые обратить внимание

* **RunFromRoof в мультиобъектном контексте:** если бот прыгает на `BigNotAlive`/`MediumNotAlive`,
  зона автоспуска (~1.9u) должна быть проверена с учётом остальных видимых объектов.
  Например, `BigNotAlive` + `SmallNotAliveRoad` сразу после — прыжок на крышу может быть
  технически безопасен, но RunFromRoof зона небезопасна из-за второго объекта.
* **Нет релевантных объектов (все Neutral):** pipeline должен явно выдать результат
  "нет шага, продолжить бег". Это тестируемое поведение.
* **Приоритет выбора объекта:** обработка идёт от ближайшего к дальнему.
  Если ближайший — Collectible на другой линии, а чуть дальше — Threat на текущей,
  бот обрабатывает ближайший. Это поведение должно быть зафиксировано в тестах.

### Общее правило для этапов 5–8

* Бот по-прежнему работает одиночными шагами — один шаг за один запуск pipeline.
* Цепочки не строятся, `ChainGenerator` / `ChainCandidate` не используются.
* После каждого завершённого шага — пересчёт, выбор нового одиночного шага.
* **Безопасность** — это безопасность одного шага в окне его исполнения.
* Допустимо не забирать `Collectible`, если для этого нужен второй шаг после уже выбранного
  one-step действия (например, `JumpOn target` → post-landing `SwitchLane` за монетой).
  Такие кейсы считаются ограничением one-step этапов, а не регрессией.

### Этап 5. Триггеры пересчёта (event-driven pipeline) — ✅ ВЫПОЛНЕН

Цель: убрать дефолтный запуск pipeline каждый кадр в `Update()`.
Pipeline запускается только по событиям.

* Реализовать отслеживание состава видимых объектов (по набору `StableId`).
  При изменении набора — триггер `VisibleObjectsChanged`.
* Триггер `StepCompleted` / `StepCancelled` — после завершения шага.
* `RunPipeline()` вызывается только при срабатывании одного из триггеров,
  а не безусловно каждый кадр.
* Pipeline запускается только в управляемых состояниях (`Run`, `RoofRun`).
* Тест: бот работает так же, как до рефакторинга (одиночные объекты этапа 4),
  но pipeline не вызывается каждый кадр — только при изменении состава объектов
  или завершении шага.

### Этап 6. Два последовательных препятствия одного типа — ✅ ВЫПОЛНЕН

* `SmallNotAliveRoad` + `SmallNotAliveRoad` — простейший последовательный сценарий.
* Бот обрабатывает первый, шаг завершается, пересчёт, обрабатывает второй.
* Тест: бот проходит два одинаковых препятствия подряд без потери жизни.

### Этап 7. Последовательность с разными категориями — ✅ ВЫПОЛНЕН

* `Threat` → `Collectible`, `Threat` → `Target`, `Target` → `Threat`.
* Пересчёт после первого шага корректно подхватывает объект другой категории.
* Тест: корректная обработка пар объектов разных категорий.

### Этап 8. Динамическое появление объектов

* Новый объект входит на экран во время исполнения текущего шага.
* `VisibleObjectsChanged` срабатывает, но не прерывает текущий шаг.
* Новый объект учитывается в следующем пересчёте после завершения шага.
* Тест: текущий шаг не ломается; следующий пересчёт корректно видит новый объект.

### Общее правило для этапов 9–12

* Бот строит цепочки из нескольких шагов.
* Используются `ProjectedState`, `ChainGenerator`, `ChainCandidate`, `ChainScorer`.
* Безопасность оценивается для цепочки целиком — если любой шаг ведёт
  к потере жизни, вся цепочка отбрасывается.

### Этап 9. Двухшаговые цепочки на одной линии

* `ProjectedState` — структура данных для проецированного состояния хомяка после шага.
* `ChainGenerator` — генерация цепочек длиной 2 (пока только на одной линии).
* Небезопасные цепочки отбрасываются целиком.
* Тест: два Threat подряд, требующих двух шагов (Jump + Jump).
  Бот генерирует двухшаговую цепочку, выполняет первый шаг.

### Этап 10. Отбрасывание небезопасных цепочек

* Сценарий: шаг 1 безопасен сам по себе, но ведёт к состоянию,
  где шаг 2 неизбежно даёт урон.
* Бот отбрасывает такую цепочку и выбирает альтернативу
  (другую линию или другой тип шага).
* Тест: бот не выбирает "ловушечный" первый шаг, ведущий в тупик.

### Этап 11. Ранжирование цепочек по профиту

* `ChainScorer` — оценка и ранжирование цепочек.
* Приоритет: безопасность → профит → энергоэффективность.
* Тест: две безопасные цепочки, одна с Target (профит), другая без —
  бот выбирает цепочку с Target.

### Этап 12. Двухшаговые цепочки с переходом линий

* `SwitchLane` + `Jump`, `SwitchLane` + `SwitchLane` back.
* `ProjectedState` корректно отражает смену линии после первого шага.
* Тест: цепочка с переходом между линиями работает корректно.

---

### Этап 13. Трёхшаговые и более длинные цепочки

* Обобщение `ChainGenerator` от фиксированной длины 2 до параметра глубины.
* Три и более препятствий подряд.
* Тест: бот строит и выполняет трёхшаговую цепочку.

### Этап 14. Крышные переходы в контексте цепочки

* Прыжок на `BigNotAlive`/`MediumNotAlive` как шаг цепочки.
* RunFromRoof safety в контексте последующих шагов: бот обязан
  просчитать, что будет в зоне автоспуска с крыши (~1.9u),
  и учесть это при оценке безопасности цепочки.
* Автопереход между смежными крышами проецируется в `ProjectedState`.
* Тест: бот отбрасывает JumpOn, если зона RunFromRoof содержит угрозу.

### Этап 15. Keep tail + extend

* Оптимизация: если хвост текущей цепочки всё ещё валиден (объекты на месте,
  путь безопасен), — не перестраивать с нуля, а достраивать новыми шагами.
* Полный rebuild только если хвост устарел.
* Повышает стабильность поведения — бот не "передумывает" без причины.
* Тест: при пересчёте бот сохраняет валидный хвост; при изменении мира — перестраивает.

### Этап 16. Ульта

* Активация ульты как шаг цепочки.
* Бот использует ульту при скоплении неизбежных угроз, которые слишком дорого
  или невозможно преодолеть обычными инструментами.
* После активации — изменение состава объектов → триггер пересчёта.
* Тест: бот активирует ульту в "безвыходном" сценарии и выживает.

### Этап 17. Полная регрессия

* Прогон всех накопленных тестовых паттернов (этапы 1–16)
  под полной системой (цепочки + пересчёт + крыши + ульта).
* Бот стабильно проходит все тестовые ситуации без потери жизни.
* 10/10 прогонов на каждом паттерне.

## Правила отладки

### Принцип изоляции

Одна итерация — одна причина. Не вносить несколько изменений одновременно.

### Три уровня анализа ошибки

| Уровень | Вопрос |
|---------|--------|
| **Решение** | Бот правильно выбрал действие? |
| **Планирование** | Цепочка корректна? (этап 9+) |
| **Исполнение** | Timing правильный? |

### Правило перехода

Не переходить к следующему этапу, пока все тестовые ситуации текущего этапа
не пройдены без ошибок (0 DAMAGE, корректные решения во всех паттернах).

### Правило фиксации прогресса

После завершения каждого этапа или значимого шага — обновить этот документ:
отметить выполненные этапы и указать следующий. Это обязательное действие
при каждом завершении работы над ботом.
