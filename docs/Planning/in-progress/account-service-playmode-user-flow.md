# Account Service PlayMode User Flow

## Цель

Описать user flow, который должны проходить PlayMode-автотесты для фичи сохранения аккаунта. Flow должен совпадать с реальным пользовательским путем, но внешний Unity backend заменяется управляемой заглушкой.

## Главный принцип

PlayMode-тест не придумывает отдельный сценарий. Он проходит тот же путь, что игрок:

```text
Меню -> Настройки -> Аккаунт: ГОСТЬ -> Сохранить -> результат привязки -> статус аккаунта
```

Разница только в исполнителе:

- в PlayMode кнопку нажимает тест;
- на устройстве кнопку нажимает человек;
- в PlayMode Unity Player Account flow возвращает fake result;
- на устройстве открывается настоящий Unity Player Account login.

## Техническая предпосылка

Для UI PlayMode-тестов нужна возможность подменить account backend на fake. Сейчас UI-контроллеры обращаются к `AccountService.Instance`, поэтому перед реализацией PlayMode-тестов нужен небольшой testability seam:

- либо `IAccountService` / `IAccountServiceProvider`;
- либо constructor injection в UI-контроллеры;
- либо test-only provider, который в runtime по умолчанию возвращает `AccountService.Instance`.

Предпочтительный вариант: маленький provider, чтобы не усложнять UI и не тащить Unity Gaming Services в UI-тесты.

## Базовый PlayMode flow: первый вход гостем

### Предусловия

- account fake настроен как signed-in guest;
- `IsLinked = false`;
- player id заполнен;
- меню загружается без автоматического sign-in prompt.

### Действия теста

1. Запустить menu scene или создать menu UI в тестовом окружении.
2. Дождаться инициализации `HomeScreen`.
3. Открыть настройки так же, как пользователь: через кнопку настроек или через `UIManager.ShowModalAsync(ScreenEnum.SettingsModal)`, если кнопка вне зоны теста.
4. Найти строку аккаунта в `SettingsModal`.

### Ожидаемый результат

- строка `Аккаунт` видна;
- статус аккаунта: `ГОСТЬ`;
- кнопка `СОХРАНИТЬ` видна и enabled;
- sign-in модалка не открывается автоматически при первом входе.

## Flow успешного сохранения прогресса

### Предусловия

- игрок в состоянии guest;
- fake account service на команду link возвращает success;
- после refresh fake возвращает `Linked`.

### Действия теста

1. Открыть настройки.
2. Убедиться, что статус `ГОСТЬ`.
3. Нажать кнопку `СОХРАНИТЬ`.
4. Подождать один кадр.
5. Проверить промежуточное состояние.
6. Завершить fake link success.
7. Подождать обновление UI.

### Ожидаемый результат

- сразу после клика кнопка становится disabled;
- статус меняется на `СОХРАНЯЕМ...`;
- после success статус становится `ПРОГРЕСС СОХРАНЁН`;
- кнопка меняет текст на `СОХРАНЕНО`;
- кнопка остается disabled;
- повторный клик невозможен.

## Flow ошибки сохранения

### Предусловия

- игрок в состоянии guest;
- fake account service возвращает `Failed`.

### Действия теста

1. Открыть настройки.
2. Нажать `СОХРАНИТЬ`.
3. Завершить fake link failed.
4. Подождать обновление UI.

### Ожидаемый результат

- во время операции кнопка disabled;
- после ошибки статус `ОШИБКА СОХРАНЕНИЯ`;
- кнопка снова enabled;
- текст кнопки снова `СОХРАНИТЬ`;
- состояние аккаунта не становится linked.

## Flow аккаунт уже используется

### Предусловия

- игрок в состоянии guest;
- fake account service возвращает `AlreadyLinked`.

### Действия теста

1. Открыть настройки.
2. Нажать `СОХРАНИТЬ`.
3. Завершить fake result `AlreadyLinked`.

### Ожидаемый результат

- статус показывает `АККАУНТ УЖЕ ИСПОЛЬЗУЕТСЯ`;
- кнопка снова enabled;
- текущий guest player не помечается как linked.

## Flow offline / ошибка проверки статуса

### Предусловия

- fake account service при проверке статуса возвращает `Offline` или `Error`.

### Действия теста

1. Открыть настройки.
2. Дождаться загрузки статуса аккаунта.

### Ожидаемый результат

- UI не падает;
- статус показывает `ОШИБКА СОХРАНЕНИЯ`;
- кнопка `СОХРАНИТЬ` остается доступной, если это соответствует текущему UX-решению;
- повторная попытка может быть выполнена тем же flow, что обычное сохранение.

## Flow уже сохраненного аккаунта

### Предусловия

- fake account service возвращает `Linked`.

### Действия теста

1. Открыть настройки.

### Ожидаемый результат

- статус `ПРОГРЕСС СОХРАНЁН`;
- кнопка `СОХРАНЕНО`;
- кнопка disabled;
- попытка повторного сохранения не запускает link flow.

## Optional flow: мягкая sign-in модалка

Этот flow тестируется только если `SigninModal` будет подключена к конкретному UX-событию, например после завершения уровня или через отдельную кнопку.

### Позже

1. Открыть `SigninModal`.
2. Нажать `ПОЗЖЕ`.

Ожидание: модалка закрывается, account state не меняется, link flow не запускается.

### Сохранить

1. Открыть `SigninModal`.
2. Нажать `СОХРАНИТЬ`.
3. Fake возвращает success.

Ожидание: статус `СОХРАНЯЕМ...`, потом `ПРОГРЕСС СОХРАНЁН`, затем модалка закрывается.

### Ошибка

1. Открыть `SigninModal`.
2. Нажать `СОХРАНИТЬ`.
3. Fake возвращает failed.

Ожидание: модалка остается открытой, кнопки снова enabled, статус объясняет ошибку.

## Что PlayMode flow не доказывает

- что настоящий Unity Player Account login откроется на Android/iOS;
- что браузерный login успешно вернет access token;
- что Unity Dashboard настроен правильно;
- что прогресс восстановится после переустановки;
- что Cloud Save синхронизирует игровые данные.

Эти пункты закрываются ручным device QA и отдельными интеграционными проверками после реализации `PlayerDataService`.

## Definition of Done для PlayMode flow

- тесты проходят тот же UI-путь, который пройдет игрок;
- UGS заменен fake-ответами, а не реальной сетью;
- проверяются начальное, промежуточное и конечное состояния UI;
- проверяются success, failed, already linked, offline/error сценарии;
- тесты не требуют Unity аккаунта, браузера и второго устройства.
