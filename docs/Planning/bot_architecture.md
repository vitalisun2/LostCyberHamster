# Архитектура бота

**Версия:** 3.0  
**Дата:** 2026-03-13  
**Назначение документа:** зафиксировать архитектурный каркас реализации бота  
**Основа:** [bot concept brainstrom](bot%20concept%20brainstrom) v4.0

---

## 1. Роль документа

Документ описывает, **каким каркасом кода и алгоритма реализуется концепт**.

Здесь фиксируются:

* основные сущности данных
* компоненты и их границы ответственности
* pipeline обработки
* алгоритм генерации и выбора цепочек
* жизненный цикл плана
* правила `keep tail + extend` и `full rebuild`

---

## 2. Архитектурные принципы

1. **SRP:** каждый компонент отвечает за одну задачу.
2. **Snapshot:** алгоритм работает по снимку мира, не по живым Unity-объектам.
3. **Pipeline:** обработка идёт по цепочке этапов, каждый этап — отдельный компонент.
4. **Projected State:** каждый шаг цепочки строится на спроецированном состоянии
   после предыдущих шагов.
5. **Разделение планирования и исполнения:** выбор маршрута отделён от тайминга.
6. **Event-driven replan:** в runtime только два триггера пересчёта.
7. **Keep tail + extend** как основной режим обновления плана.
8. **Полный rebuild** как fallback, когда хвост плана больше не подходит.

---

## 3. Обзор pipeline

Алгоритм бота устроен как pipeline из последовательных этапов.
Каждый этап — отдельный компонент с одной ответственностью.

```
Trigger
  → HamsterBot (orchestrator)
    → SnapshotBuilder       → BotSceneSnapshot
    → ObjectClassifier       → ObstacleInfo[] с категориями
    → PlanValidator          → keep tail / rebuild решение
    → ChainGenerator         → List<ChainCandidate>
    → ChainScorer            → оценённые кандидаты
    → PlanSelector           → CurrentPlan
  → BotTimingPolicy          → исполнение головы очереди
```

Orchestrator вызывает этапы по порядку и передаёт результат каждого
следующему. Компоненты pipeline **не знают друг о друге** — они работают
только со своими входными и выходными данными.

## 4. Сущности данных

### `BotSceneSnapshot`

Снимок мира на момент запуска алгоритма.

Содержит:

* текущую линию хомяка
* пространство: дорога или крыша
* энергию
* жизни
* заряд ульты
* монеты
* список видимых объектов (ещё не классифицированных)

Snapshot собирается один раз за запуск алгоритма и далее не меняется.

### `ObstacleInfo`

Снимок данных об одном видимом объекте.

Содержит:

* тип (`ObstacleTypeEnum`)
* линию (верхняя / нижняя)
* флаг крыши
* координаты (leftX, rightX, centerX)
* расстояние до хомяка
* категорию (`Target` / `Threat` / `Collectible` / `Neutral`)
* устойчивую ссылку или ID объекта

### `ProjectedState`

Ожидаемое состояние хомяка после уже добавленных шагов в цепочке.

Содержит:

* линию
* пространство: дорога / крыша
* примерную X-позицию
* энергию
* заряд ульты
* набор ещё не обработанных объектов

`ProjectedState` — это входные данные для генерации **следующего** шага.
Начальный `ProjectedState` строится из `BotSceneSnapshot`.
Каждый добавленный шаг порождает новый `ProjectedState`.

### `ChainCandidate`

Одна кандидатная цепочка, сгенерированная `ChainGenerator`.

Содержит:

* список шагов (`ChainStep[]`)
* финальный `ProjectedState` после последнего шага
* суммарную стоимость по энергии
* флаг безопасности (все шаги безопасны)
* суммарную выгоду (количество уничтоженных целей, собранных бонусов)

### `CurrentPlan`

Текущий рабочий план бота.

Содержит:

* очередь шагов (`ChainStep[]`)
* стратегию / причину выбора (строка для логирования)

### `ChainStep`

Один шаг в цепочке.

Содержит:

* действие (`BotAction`)
* целевой объект (ссылка на `ObstacleInfo`)
* условие исполнения (дистанция до объекта)
* стоимость по энергии
* ожидаемое взаимодействие (описание результата)
* статус

### Статусы шага

* `ready` — ждёт исполнения
* `in_progress` — действие отправлено, ждём завершения
* `completed` — действие завершено

## 5. Компоненты и их ответственности

### `HamsterBot`

**Роль:** runtime-оркестратор.

**Отвечает за:**

* приём runtime-триггеров (завершение шага, изменение состава объектов)
* проверку, что хомяк в управляемом состоянии (`Run` / `RoofRun`)
* очистку completed-шагов из головы текущего плана
* вызов этапов pipeline по порядку
* хранение `CurrentPlan`
* передачу головы очереди в `BotTimingPolicy`

**Не отвечает за:** принятие решений, классификацию, оценку.

### `SnapshotBuilder`

**Роль:** сборщик снимка мира.

**Вход:** живые Unity-объекты (Hamster, ObstacleSpawner).

**Выход:** `BotSceneSnapshot`.

**Отвечает за:**

* чтение состояния хомяка (линия, пространство, энергия, жизни, ульта, монеты)
* сканирование видимых объектов в диапазоне
* построение списка сырых `ObstacleInfo` (без категорий)

Это **единственный компонент**, который обращается к живым Unity-объектам.
Все остальные работают только с данными snapshot.

### `ObjectClassifier`

**Роль:** классификация объектов.

**Вход:** `BotSceneSnapshot` с некатегоризированными объектами.

**Выход:** `ObstacleInfo[]` с проставленными категориями.

**Отвечает за:**

* присвоение каждому объекту категории:
  `Target`, `Threat`, `Collectible`, `Neutral`
* учёт контекста: один и тот же тип объекта может быть Target
  с крыши и Threat с дороги

### `PlanValidator`

**Роль:** проверка актуальности текущего плана.

**Вход:** `BotSceneSnapshot`, текущий `CurrentPlan`.

**Выход:** решение: `keep tail` или `rebuild`.

**Отвечает за:**

* проверку, что объекты оставшихся шагов всё ещё на экране
* проверку, что путь до ближайшего шага безопасен
* проверку, что хвост соответствует текущим целям
* обнаружение более приоритетной достижимой цели

Если хвост валиден — orchestrator пропускает генерацию, передаёт
хвост на достройку. Если невалиден — запускается полная генерация.

### `ChainGenerator`

**Роль:** генерация кандидатных цепочек.

**Вход:** `ObstacleInfo[]`, начальный `ProjectedState` (из snapshot).

**Выход:** `List<ChainCandidate>`.

**Отвечает за:**

* построение цепочек шаг за шагом
* ветвление: для каждого объекта на пути — несколько
  вариантов действий (смена линии, прыжок, суперпрыжок, на крышу, и т.д.)
* проекцию состояния вперёд через `ProjectedState`
* учёт автоматических переходов (RunFromRoof, автопереход между крышами)
* отсечение цепочек, где любой шаг ведёт к потере жизни

Подробно алгоритм описан в разделе 8.

### `ChainScorer`

**Роль:** оценка кандидатных цепочек.

**Вход:** `List<ChainCandidate>`.

**Выход:** `List<ChainCandidate>` с заполненными оценками.

**Отвечает за:**

* ранжирование по приоритетам из концепта:
  1. безопасность (небезопасные уже отсечены, но проверка — страховка)
  2. минимальная стоимость по энергии
  3. максимальная выгода (уничтоженные цели, собранные бонусы)

### `PlanSelector`

**Роль:** выбор лучшей цепочки и формирование плана.

**Вход:** оценённые `ChainCandidate[]`, текущий `CurrentPlan` (если keep tail).

**Выход:** обновлённый `CurrentPlan`.

**Отвечает за:**

* в режиме keep tail: достройку хвоста новыми шагами
* в режиме rebuild: выбор лучшего кандидата и создание нового плана
* формирование причины выбора (для логирования)

### `BotTimingPolicy`

**Роль:** точное исполнение шагов.

**Вход:** голова очереди `CurrentPlan`.

**Выход:** игровое событие в нужный момент.

**Отвечает за:**

* проверку, можно ли выполнять шаг прямо сейчас
* ожидание правильного момента (дистанция до объекта)
* проверку через CollisionUtils для JumpOn и JumpOver
* отправку реального игрового события (JumpRequest, TapRequest, и т.д.)
* перевод шага в `in_progress`, затем в `completed`

## 6. Runtime-триггеры

Алгоритм запускается только в `Run` и `RoofRun`.

После включения бота допускается стартовое построение плана.
Дальше в runtime только два триггера:

1. завершился шаг из головы очереди, и хомяк снова управляем
2. изменился **состав** объектов в видимой области экрана

Изменение состава определяется по идентичности набора объектов:

* вход нового объекта справа
* выход старого объекта слева
* уничтожение препятствия
* сбор collectible

---

## 7. Модель плана

### FIFO-очередь

`CurrentPlan` работает как очередь:

* новые шаги добавляются в хвост
* исполняется шаг из головы
* completed-шаги удаляются из головы

### Правило удаления

* шаг получает `completed` после фактического завершения действия
* физически удаляется в начале следующего запуска алгоритма
* за один запуск может быть удалено несколько completed-шагов

## 8. Алгоритм генерации цепочек

### Начальное состояние

`ChainGenerator` получает классифицированные объекты и начальный
`ProjectedState`, построенный из snapshot:

* линия хомяка
* пространство (дорога / крыша)
* энергия, ульта
* все видимые объекты впереди

### Цикл построения

Генерация идёт итеративно — от ближайшего объекта к дальнему:

1. взять текущий `ProjectedState`
2. найти ближайший релевантный объект (Threat или Target на пути)
3. если объект — Threat: сгенерировать варианты уклонения
4. если объект — Target: сгенерировать варианты взаимодействия + уклонения
5. для каждого варианта: применить шаг к `ProjectedState` → получить новый
6. рекурсивно продолжить для нового состояния
7. если ни одного объекта впереди нет — цепочка завершена

### Ветвление

Каждый объект на пути может порождать несколько вариантов:

* сменить линию (бесплатно)
* перепрыгнуть (10 энергии)
* суперпрыжок (20 энергии)
* напрыгнуть на цель (10 энергии, если Target)
* запрыгнуть на крышу (10 энергии, если bigNotAlive/mediumNotAlive)
* прыгнуть с крыши вниз (10 энергии)
* ульта (0 энергии, нужен полный заряд)

Не все варианты допустимы в каждой ситуации. Недопустимые отсекаются
сразу (нет энергии, не тот тип объекта, и т.д.).

### Проекция автоматических переходов

При проекции `ProjectedState` учитываются автоматические переходы:

* **RunFromRoof:** если projected-позиция за краем крыши —
  проецируется спуск (~1.9 юнитов уязвимости).
  Если в зоне спуска стоит угроза — шаг небезопасен.
* **Автопереход между крышами:** если следующий транспорт вплотную —
  проецируется продолжение RoofRun.
* **Отскок после JumpOn:** проецируется зона приземления после отскока.
  Если там угроза — шаг небезопасен.

### Отсечение

Цепочка **отбрасывается целиком**, если хотя бы один шаг
неизбежно ведёт к потере жизни.

### Ограничение глубины

Генерация ограничена горизонтом 2-5 шагов. Обычно достаточно 2-4.
Это определяется количеством релевантных объектов на видимом экране.

## 9. Оценка и выбор цепочки

### Критерии оценки

`ChainScorer` оценивает каждый `ChainCandidate` по трём критериям
в порядке приоритета:

1. **Безопасность** — все шаги безопасны (после отсечения в генераторе
   это должно быть true, но проверка — страховка)
2. **Стоимость** — суммарная трата энергии (меньше = лучше)
3. **Выгода** — количество уничтоженных Target + ценность собранных
   Collectible (больше = лучше)

### Логика выбора

`PlanSelector` берёт оценённых кандидатов и:

* отбрасывает небезопасных (если таковые прошли)
* из оставшихся выбирает с минимальной стоимостью
* при равной стоимости — с максимальной выгодой

## 10. Правила обновления плана

### Pipeline при keep tail

Если `PlanValidator` решает, что хвост текущего плана валиден:

1. хвост передаётся в `ChainGenerator` как начальная точка
2. начальный `ProjectedState` строится из **конца хвоста**, а не из snapshot
3. генератор достраивает цепочку
4. `PlanSelector` объединяет хвост с достроенной частью

### Pipeline при full rebuild

Если хвост невалиден:

1. `ChainGenerator` строит цепочки с нуля (от текущего snapshot)
2. `ChainScorer` оценивает все кандидаты
3. `PlanSelector` выбирает лучшего и создаёт новый `CurrentPlan`

### Когда rebuild

* объекты оставшихся шагов исчезли с экрана
* путь до ближайшего шага больше не безопасен
* появилась более приоритетная достижимая цель
* хвост нельзя безопасно продолжить

## 11. Runtime-пайплайн (полная последовательность)

Каждый запуск алгоритма:

1. сработал runtime-триггер
2. `HamsterBot` проверяет `Run` или `RoofRun`
3. из головы `CurrentPlan` удаляются completed-шаги
4. `SnapshotBuilder` собирает `BotSceneSnapshot`
5. `ObjectClassifier` классифицирует объекты
6. `PlanValidator` решает: keep tail или rebuild
7. `ChainGenerator` генерирует кандидатные цепочки
   (от хвоста при keep tail, с нуля при rebuild)
8. `ChainScorer` оценивает кандидатов
9. `PlanSelector` формирует обновлённый `CurrentPlan`
10. голова очереди передаётся в `BotTimingPolicy`
11. timing policy ждёт окно и отправляет игровую команду
12. шаг → `in_progress` → `completed`

---

## 12. Итоговая формула

```
Trigger
  → Snapshot → Classify → Validate Tail
    → Generate Candidates → Score → Select
      → Execute Head
```

Где:

* **Pipeline** — последовательность независимых этапов
* **ProjectedState** — механизм построения шагов вперёд
* **ChainCandidate** — кандидатная цепочка с оценкой
* **Keep tail + extend** — основной режим обновления
* **Full rebuild** — fallback при невалидном хвосте
* **Два runtime-триггера** — завершение шага и изменение состава объектов
