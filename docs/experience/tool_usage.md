# Использование инструментов

## Сначала узкий проектный инструмент

**Ситуация.** Задачу можно выполнить общей командой или готовым проектным инструментом.

**Действия.**

1. Проверить доступность инструмента и найти команду через его discovery/status.
2. Выбрать узкую проектную команду со структурированным результатом.
3. Общий `eval` или ручной probe использовать для разовой гипотезы.
4. Повторяемую операцию оформить именованной проектной командой.

**Результат.** Действие воспроизводимо, входы явны, результат читается без разбора UI и шумного лога.

## Использовать штатную диагностику

**Ситуация.** Нужны runtime-факты.

**Действия.**

1. Выбрать владельца события и диагностический канал.
2. Использовать профильный helper. Недостающий метод добавить в его diagnostics-класс.
3. Читать только нужный канал, событие и хвост лога.

**Результат.** Диагностика остаётся фильтруемой и не создаёт ad-hoc logger.

## Читать документацию по карте

**Ситуация.** Большой справочник содержит много несвязанных тем.

**Действия.**

1. По карте выбрать только темы текущего scope.
2. Прочитать их до плана или правки.
3. При изменении scope обновить выбор, не перечитывать весь справочник.

**Результат.** Нужные ограничения учтены без лишнего чтения.

## Сначала инвентаризация, потом чтение

**Ситуация.** Исследование охватывает много документов или файлов.

**Действия.**

1. Собрать список файлов и узкие совпадения через `rg --files` и `rg -n`.
2. Сгруппировать кандидатов по теме.
3. Читать выбранные файлы полностью малыми пакетами.
4. Усечённый вывод сразу разбить на меньшие запросы; выводы по неполному контексту не делать.

**Результат.** Релевантный контекст прочитан полностью без шумного общего dump и повторной работы.

## Компактный вывод результатов генерации

**Ситуация.** Инструмент возвращает изображение как data URL вместе с путём сохранения.

**Действия.** Показывать изображение через `generatedImage(result)`. В `text` и `notify` передавать только статус, имя варианта и `output_hint`. Полный результат сохранять через `store` для следующих вызовов.

**Результат.** Изображение доступно пользователю, текстовый вывод остаётся коротким.

Источники: [Unity CLI](../rules/unity_cli.md), [Agent Tools](../rules/agent_tools.md), [Clean Code: как использовать](../clean_code_by_b_martin/README.md).

## Восстанавливать Docker после ошибки служебных сокетов

Если Docker Desktop падает на `dockerInference` или `docker-secrets-engine/engine.sock` с ошибкой 1920, сначала сопоставить свежий startup log и метаданные конкретных файлов. В подтверждённом случае оба каталога содержали только пустые runtime-сокеты. Остановить Docker, сохранить оба каталога переименованием в соседние резервные папки и выполнить один запуск. Проверить абсолютные пути и содержимое перед переносом. Каждый неудачный запуск может вновь оставить сокет, поэтому оба места проверять вместе. Отключение Model Runner само по себе не отменяет создание его listener.

После восстановления проверить `docker ps`, порт и restart policy нужного контейнера, затем `getMe` и `getChat` из настроенного Telegram helper. Сохранившийся контейнер использовать повторно. APK отправлять по точному пути из build summary; сохранять подтверждённый `message_id`, размер и buildId рядом с артефактом.

При диагностике процессов выводить PID, имя и путь executable. Полная command line дочернего Unity CLI может содержать временный access token.
