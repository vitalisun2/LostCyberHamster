# Android Dev Build Automation Menu

Дата: 2026-07-03

## Идея

Сделать в Android development build небольшой developer/test menu, который позволит прямо на телефоне:

- включать и выключать игрового бота;
- запускать автоматические проверки пользовательских flow;
- получать структурированные логи выполнения на локальный device log collector.

Первый целевой сценарий для такого меню: автоматический прогон tutorial flow на реальном Android-устройстве.

Это не замена проверкам в Unity Editor, а дополнительный слой E2E-регрессии на настоящем устройстве. Editor нужен для быстрого цикла разработки, Android dev build нужен для проверки реального runtime: touch input, Android lifecycle, Addressables в билде, сохранения, HTTP-логирование, производительность, порядок загрузки сцен и UI.

## Зачем это нужно

Сейчас уже есть бот для тестирования уровней и сбора регрессов. Он долго развивался, стабилизирован и хорошо показывает себя на игровых уровнях. Хочется использовать эту инфраструктуру шире:

- быстро смотреть, как игра проходит уровень с ботом на телефоне;
- при необходимости выключать бота и играть руками;
- запускать автоматические проверки UI/use-case сценариев;
- не зависеть только от Unity Editor, потому что часть проблем проявляется только в Android build;
- собирать логи с установленной игры без скриншотов и ручной расшифровки состояния;
- позже использовать такие проверки по расписанию или перед публикацией очередного APK.

## Ценность

### Реальное устройство как регрессионный стенд

Android build проверяет то, что Editor не обязан воспроизводить один в один:

- реальные tap/touch события;
- поведение UI Toolkit в сборке;
- порядок загрузки Addressables;
- Android permissions и HTTP-доступ к локальному collector;
- работу сохранений после установки и очистки данных;
- поведение игры при смене экранов, переходах и загрузке уровней;
- отличия Development Build и обычного release build.

### Быстрая ручная проверка

Developer menu позволит в одном и том же APK переключаться между режимами:

- `Bot On` - игра сама проходит уровень, удобно смотреть общий runtime;
- `Bot Off` - можно играть руками;
- `Run Tutorial Flow` - запустить готовый автосценарий и смотреть результат по логам.

### Основа для будущего набора E2E сценариев

Потенциальные future flow:

- tutorial flow;
- покупка и экипировка скина;
- получение награды за quest;
- переходы по основным меню;
- покупка/использование расходников;
- завершение уровня и переход к следующему;
- проверка сохранения прогресса между перезапусками;
- smoke test первого уровня первой локации.

## Принципиальный подход

Developer/test menu должен быть dev-only инфраструктурой поверх игры.

Основная игра не должна зависеть от automation runner. В релизной сборке это меню и сценарии должны быть отключены или полностью недоступны через compile/runtime guard.

Правильная модель:

- игра живет своим обычным runtime;
- developer menu запускается только в `UNITY_EDITOR` или `Development Build`;
- automation runner действует как внешний пользователь: вызывает те же публичные handlers/intent-слой, которые использует UI и gameplay;
- сценарии не патчат игровой flow, а проходят его через существующую инфраструктуру;
- результаты сценариев пишутся в device log collector.

## Компоненты

### Dev Menu Entry Point

Небольшая кнопка поверх UI, видимая только в development окружении.

Варианты отображения:

- маленькая полупрозрачная кнопка в углу экрана;
- кнопка открывает компактную панель;
- панель можно закрыть;
- панель не должна мешать обычной игре.

Guard:

- `UNITY_EDITOR`;
- `Debug.isDebugBuild`;
- отдельная настройка `DevToolsEnabled`, если понадобится.

### Developer Menu Panel

Минимальный первый состав:

- toggle `Bot`;
- button `Run Tutorial Flow`;
- текстовый статус последнего запущенного сценария;
- button `Close`.

Позже можно добавить:

- список сценариев;
- выбор скорости сценария;
- reset save data;
- open first level;
- upload logs now;
- copy device/session id;
- show collector endpoint.

### Bot Toggle

Переключатель должен управлять текущим runtime-ботом без изменения обычной архитектуры игры.

Ожидаемое поведение:

- `Bot On`: бот управляет gameplay input;
- `Bot Off`: игрок управляет руками;
- состояние переключателя применяется только в dev build;
- переключатель не должен ломать tutorial, где внешний бот должен быть подавлен tutorial runtime.

Важно отдельно развести:

- gameplay bot для прохождения уровней;
- tutorial automation runner для проверки user flow;
- tutorial runtime, который обучает игрока.

Это разные роли. Их нельзя смешивать в один глобальный флаг без явной модели приоритетов.

### Automation Runner

Единая точка запуска dev-сценариев.

Ответственность:

- принять команду `Run Tutorial Flow`;
- подготовить начальное состояние сценария;
- запустить сценарий;
- выполнить шаги с заданной задержкой;
- логировать каждый этап;
- вернуть финальный результат: success/fail/timeout/canceled.

Runner не должен напрямую знать детали всех экранов. Для каждого flow лучше иметь отдельный сценарий/driver.

### Flow Definition

Каждый сценарий описывается как последовательность шагов.

Пример абстрактной модели:

- `ResetTutorialState`;
- `OpenFirstLocationFirstLevel`;
- `WaitForTutorialStep(1)`;
- `PerformTutorialAction(DodgeTap)`;
- `WaitForTutorialStep(2)`;
- `PerformTutorialAction(Jump)`;
- ...
- `OpenHomeFromTutorialReward`;
- `OpenCharacterScreen`;
- `SelectLightningSkin`;
- `BuySkin`;
- `EquipSkin`;
- `RunTutorialLevel2`;
- `UseSuperHit`;
- `AssertTutorialCompleted`.

Для каждого шага:

- имя;
- timeout;
- precondition;
- action;
- expected result;
- лог start/end/error.

### Intent/Action Adapter

Для UI Toolkit и gameplay действий нужен слой, который выполняет действие максимально близко к пользовательскому поведению.

Возможные действия:

- tap по конкретной gameplay-зоне;
- click по UI element;
- вызвать публичный handler/command, если это ровно тот же путь, что использует UI;
- ждать появления элемента;
- ждать смены экрана;
- ждать загрузки уровня;
- ждать конкретного tutorial stage.

Приоритет:

1. Использовать существующие handlers/intent-слой, если они отражают реальное действие пользователя.
2. Использовать корректный synthetic click/tap для UI Toolkit, если нужно проверить именно input pipeline.
3. Не обращаться к приватным внутренностям экранов без необходимости.

### Device Log Collector Integration

Каждый сценарий должен писать структурированные события в логи, которые уходят на локальный collector.

Минимальные события:

- `dev_menu_opened`;
- `bot_toggled`;
- `flow_started`;
- `flow_step_started`;
- `flow_step_completed`;
- `flow_step_failed`;
- `flow_timeout`;
- `flow_completed`;
- `flow_canceled`;
- `runtime_error`.

Для каждого события полезные поля:

- build label;
- device id/model;
- session id;
- flow id;
- step id;
- screen name;
- level/location/daypart;
- tutorial stage;
- bot enabled;
- elapsed ms;
- error message;
- stack trace для exception.

Цель: после ручного запуска на телефоне агент может прочитать логи в `DeviceLogs/android` и понять, какой flow прошел, где упал и почему.

## Первый сценарий: Run Tutorial Flow

### Начальное состояние

Перед запуском:

- отключить gameplay bot или явно перевести его под контроль сценария;
- сбросить `tutorial completed` в false;
- подготовить tutorial sandbox state;
- убедиться, что активный skin в tutorial state - default;
- убедиться, что для tutorial skin lesson есть тренировочные ресурсы;
- не портить реальное игровое состояние игрока.

### Запуск

Сценарий должен имитировать обычный путь игрока:

1. Открыть игру.
2. Перейти к выбору первого уровня первой локации.
3. Запустить первый уровень.
4. Вместо обычного уровня должен стартовать tutorial flow, если tutorial еще не completed.

### Игровая часть tutorial

Проверить шаги:

- уклониться;
- перепрыгнуть;
- напрыгнуть;
- super jump для перепрыгивания;
- super jump для напрыгивания;
- запрыгнуть на крышу;
- перепрыгнуть с крыши на крышу;
- напрыгнуть с крыши.

Для каждого шага:

- дождаться остановки tutorial;
- проверить активную подсветку;
- выполнить нужное действие;
- дождаться успешного продолжения;
- проверить, что хомяк не потерял жизнь.

### UI часть tutorial

После основной части:

1. Показать сообщение о том, что игрок освоил основное управление.
2. Дать тренировочные кристаллы в sandbox state.
3. Подсветить переход в меню.
4. Подсветить переход в character/skins screen.
5. Подсветить переключение на lightning skin.
6. Подсветить покупку.
7. Подсветить экипировку.

Важно: переходы должны происходить через тот же UI flow, что и у пользователя. Не должно быть скрытого телепорта между экранами, если обычный игрок так сделать не может.

### Финальная часть tutorial

После экипировки lightning skin:

1. Запустить `Tutorial Level 2`.
2. Довести хомяка до финального паттерна.
3. Остановить игру перед препятствиями.
4. Подсветить кнопку super hit.
5. Выполнить super hit.
6. Дождаться, пока эффект полностью отработает и препятствия уничтожатся.
7. Показать финальную модалку: `Поздравляем, вы прошли обучение`.
8. Проверить наличие кнопок `Играть` и `Меню`.
9. Записать `flow_completed`.

## Скорость сценариев

Для dev automation можно иметь настройку delay между шагами.

Первый практичный режим:

- задержка 1 секунда между user-action шагами;
- ожидания состояния должны быть event-driven или timeout-based, а не fixed sleep;
- игровой tutorial для пользователя должен идти со скоростью 1.0;
- ускорение допустимо только для внутренних automation проверок, если оно явно включено.

Важно: скорость автопрогона не должна менять пользовательский tutorial runtime в обычном прохождении.

## Архитектурные ограничения

- Не добавлять зависимости обычного UI на developer menu.
- Не смешивать gameplay bot и UI automation runner.
- Не хранить dev-only состояние в обычном сохранении игрока без явной причины.
- Не делать релизную функциональность зависящей от dev tools.
- Не ломать текущий loading pipeline.
- Не менять сигнатуры существующих loading/runtime методов без доказанного корня проблемы.
- Не использовать workaround вместо явной модели состояния.
- Любой сценарий должен иметь понятные логи и timeout.

## Предложенная структура

Возможная структура кода:

```text
Assets/Scripts/DevTools/
  DevToolsBootstrap.cs
  DevToolsMenuController.cs
  DevToolsRuntimeState.cs

Assets/Scripts/DevTools/Automation/
  DevAutomationRunner.cs
  DevAutomationFlow.cs
  DevAutomationStep.cs
  DevAutomationResult.cs
  DevAutomationLogger.cs

Assets/Scripts/DevTools/Automation/Flows/
  TutorialFlowAutomation.cs

Assets/Scripts/DevTools/Bot/
  DevBotToggleController.cs
```

Если существующая архитектура уже имеет подходящее место для test/automation инструментов, структуру нужно адаптировать под нее, а не создавать параллельный мир.

## Проверки перед реализацией

Перед кодом нужно проверить:

- где сейчас создается и управляется runtime bot;
- какой публичный механизм включает/выключает управление ботом;
- где лучше разместить dev-only overlay;
- как сейчас открываются UI screens;
- какие события/handlers вызываются при кликах игрока;
- как tutorial automation уже выполняет действия;
- как device log reporter стартует в Android build;
- не попадает ли dev menu в non-development build.

## Минимальный MVP

MVP можно сделать в несколько небольших шагов:

1. Dev-only кнопка открытия меню на Android development build.
2. Панель с toggle `Bot` и button `Run Tutorial Flow`.
3. Подключить toggle к существующему runtime bot.
4. Подключить `Run Tutorial Flow` к существующему tutorial automation/intent runner.
5. Добавить структурированные логи flow events.
6. Собрать APK, установить на Android, проверить:
   - меню открывается;
   - bot toggle работает;
   - tutorial flow запускается;
   - события уходят в локальный collector.

## Расширение после MVP

После стабилизации tutorial flow можно добавить:

- `Run First Level Bot Smoke`;
- `Run Skin Purchase Flow`;
- `Run Quest Reward Flow`;
- `Run Save/Restart Flow`;
- `Run All Smoke Flows`;
- экспорт последнего результата в отдельный JSON;
- запуск сценария по command line/deep link;
- запуск сценариев по расписанию через установленный APK;
- отображение краткого результата на экране.

## Риски

### Dev tools могут протечь в релиз

Нужны compile/runtime guards и проверка non-development build.

### Automation начнет обходить реальный UI

Если сценарии будут напрямую менять состояние, они перестанут быть E2E проверками. Нужно использовать реальные handlers/intent pipeline.

### Bot и tutorial начнут конфликтовать

Нужна явная модель приоритетов:

- tutorial runtime может подавлять gameplay bot;
- automation runner управляет только своим flow;
- ручной игрок должен иметь возможность выключить bot.

### Логи станут шумными

Нужно структурировать события и не писать огромный поток каждый frame. Для сценариев важнее этапы, действия, state transitions и ошибки.

## Итог

Идея выглядит правильной и полезной: Android development build с developer menu превращает телефон в реальный E2E-регрессионный стенд. Это особенно ценно для tutorial и UI use cases, потому что они зависят от настоящего mobile runtime сильнее, чем чистая gameplay-логика уровня.

Оптимальный путь: оставить Unity Editor проверки для быстрой разработки, а Android dev menu использовать как второй слой smoke/regression проверок перед отправкой APK и во время ручного тестирования на телефоне.
