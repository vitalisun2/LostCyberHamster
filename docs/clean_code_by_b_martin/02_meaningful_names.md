# Содержательные имена

## Концепция

Имя должно передавать намерение. Хорошее имя отвечает на вопросы: что это, зачем используется, в каком контексте живет. Если смысл приходится восстанавливать по телу метода или по соседним строкам, имя слабое.

## Когда читать

- Переименование классов, методов, полей, локальных переменных.
- Добавление нового public/internal API.
- Рефакторинг кода с `data`, `info`, `manager`, `temp`, `result1`, `flag`.

## Правила

- Называй по роли в домене, а не по случайной реализации.
- Избегай шумовых слов: `Data`, `Info`, `Object`, если они не добавляют смысла.
- Не используй одно слово для разных концепций.
- Не используй разные слова для одной концепции без причины.
- Чем шире область видимости, тем точнее и длиннее должно быть имя.
- Имя метода должно описывать действие и честно отражать побочные эффекты.

## Пример

Плохо: имена заставляют читать тело, чтобы понять предметную область.

```csharp
var list = planner.GetData(a, b);
if (list.Count > 0)
{
    Do(list[0]);
}
```

Лучше: имена раскрывают сценарий без погружения в детали.

```csharp
IReadOnlyList<JumpCandidate> roofExitCandidates =
    jumpPlanner.FindRoofExitCandidates(hamsterPosition, roofBounds);

if (roofExitCandidates.Count > 0)
{
    SelectJumpTarget(roofExitCandidates[0]);
}
```

## Чеклист ревью

- Можно ли понять назначение переменной по одной строке объявления?
- Не скрывает ли имя единицы измерения, координатную систему или режим?
- Не выглядит ли метод безобидным, хотя меняет состояние?
- Не появился ли новый термин, который дублирует существующий термин проекта?

## Правило для агента

Если для объяснения имени нужна фраза "ну это такая штука, которая...", имя нужно уточнить или код нужно разложить на более явные концепции.
