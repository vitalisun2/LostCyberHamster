# Комментарии

## Концепция

Комментарий не должен компенсировать плохое имя, длинную функцию или неявный сценарий. Лучший комментарий часто заменяется переименованием, извлечением метода или уточнением типа. Хороший комментарий объясняет намерение, предупреждает о важном ограничении или фиксирует контекст, который не выражается кодом.

Проектное правило про XML-summary и комментарии внутри сложных методов остается обязательным и имеет приоритет.

## Когда читать

- Добавляются или обновляются комментарии.
- Код непонятен и хочется объяснить его текстом.
- Есть устаревший TODO, закомментированный код или шумовой комментарий.

## Правила

- Комментируй "почему", риск или внешний контракт, а не очевидное "что".
- Не оставляй закомментированный код.
- Не добавляй шум вроде `// increment index`.
- TODO должен быть конкретным и проверяемым.
- Если комментарий пересказывает имя метода, улучши имя.
- При изменении поведения обнови XML-summary.

## Пример

Плохо:

```csharp
// Check roof
if (sensor.HasRoofAhead && bot.Speed > 0)
{
    // Start roof run
    bot.StartRoofRun();
}
```

Лучше:

```csharp
if (CanEnterRoofRun(sensor, bot))
{
    bot.StartRoofRun();
}
```

Комментарий уместен, когда код связан с внешним ограничением:

```csharp
// Unity animation sampling in edit mode must use AnimationMode; Animator.Play
// does not advance clips reliably outside Play Mode.
AnimationMode.SampleAnimationClip(target, clip, time);
```

## Правило для агента

Перед добавлением комментария попробуй сделать код самодокументируемым. Оставляй комментарий только там, где он сохраняет знание, которого нет в коде.
