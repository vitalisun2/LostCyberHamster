# 16 — Игровой день, неделя и Claim

2026-09-09. Статус: рекомендуемый минимальный контракт блока3 и условный серверный вариант. Решение о единой миграции Daily/W1 принадлежит пользователю/основному чату. [Основа13](13_return_engagement.md), [план](../return_engagement_plan.md).

По последующему поручению09.09 реализован рабочий вариантUTC+L; Daily/W1 сохраняют свои правила. Восстановление локальной истории без replay валюты доступно явным действием в подробностях. ServerS не активирован. Реальныеfault/clock/cloud/offline-прогоны пользователь оставил себе; [отчёт](../return_engagement_implementation.md).

## Проверенная граница

- `DailyQuestService`/scheduler: локальная дата устройства, `UsedGenerationDates`, незабранные completed-слоты и FIFO общих наград.
- Блок2 W1: `WeeklyLeaderboardRun.RewardDecision` содержит `RewardId=RunId`, `FirstConfirmedAtUtc`, `UtcDate`, `AwardedExperience`, `IsLegacyReward`; `AppliedWeeklyRewardRunIds` отмечает решения0/5. Квота owner/environment/date общая по доскам локального журнала. API рекорда не предоставляет trusted timestamp и atomic daily claim.
- `LevelManager.CompleteLevel(levelKey,stars)` транзакционно сохраняет best/XP, после commit публикует `LastCompletionExperience`. Это квитанция XP; `Source=progressKey` не уникален для повторного забега. `WeeklyRun.RunId` принадлежит leaderboard, поэтому не подходит для всех обычных побед.
- `GameDataManager.ExecuteTransaction` сохраняет gameplay и journal до уведомлений, откатывает mutation при ошибке; вложенные транзакции отклоняет. `GetJournalJson/SetJournalJson` поддерживают owner-scoped локальный журнал. Cloud snapshot содержит PlayerData; owner journals остаются на устройстве при выборе cloud baseline. Значит перенос receipts и перенос технического журнала — разные контракты.
- `QuestManager.GetDailyCommonReward()` возвращает `DailyCommonRewardSnapshot(ProfileId,Generation,SetId,OriginDate,RewardType,Amount,RemainingRewards)`. `ClaimDailyCommonReward(snapshot)` проверяет предъявленный контекст. Новая активность использует тот же принцип expected snapshot, собственный доменный сервис и ID.

Источники: прочитанные затронутые файлы в `Assets/Scripts/GameManagement/Persistence/`, `System/LevelManagement/LevelManager.cs`, `CloudSave/ConflictService.cs`, `SharedCore/Meta/Quests/Daily/DailyCommonRewardSnapshot.cs`; прямая передача владельца2 от09.09. Финальный код блока2 ещё в работе, API перепроверить P3-00.

## Выбор для реализации

Сначала выбрать границу периода; затем отдельно — доверие к источнику времени. Это два разных решения.

| Граница новых активностей | UX и совместимость | Цена/риск |
|---|---|---|
| Тот же local-день, что Daily | Все обычные «награды дня» сбрасываются в местную полночь; проще объяснить «Сегодня/Завтра». Неделя начинается в местный понедельник. W1 остаётся своим UTC-first-confirmation | Смена timezone/DST меняет расписание по устройству; неделя разных устройств может различаться. Нужно точно повторить provider Daily и согласовать future GameDay с владельцем2 |
| **UTC-день, Daily остаётся local** | Фиксированное время активности/недели при поездках и смене timezone; единый момент конца недели для всех, перенос будущего backend проще | Игрок имеет **два времени обновления**. Home обязан показывать точную границу активности; Daily — свою. UTC из клиентских часов имеет тот же предел доверия, что local |

Предпочтение для этого плана — UTC: у недельной цели устойчивый общий срок и предсказуемый остаток после смены часового пояса. UX-плата реальна: два обновления. В Home использовать «Награда дня · следующий шаг после03:00», а в подробностях «Активности00:00 UTC (03:00 на устройстве); Daily00:00 на устройстве» для Москвы. В промежутке00:00–03:00 слово «Завтра» без времени ошибочно. Если основной чат ставит простоту общего «Сегодня» выше единого срока недели, local-вариант готов к выбору: меняется provider и календарные fixtures, domain/Claim/суммы остаются теми же.

Будущий единый `GameDay` — shared-контракт с владельцем2: источники `DailyQuestScheduler`/`DailyQuestService`, `QuestManager` ротации, W1 `WeeklyLeaderboardCoordinator`/`RewardDecision`, PlayerData/validator и общие подписи времени. Сначала согласовать границу и cutover, затем передать файлы. Даже при одном provider W1 сохраняет семантику первого подтверждения, Daily — набора, цикл — Win; одинаковое время не объединяет три квоты. Эти правки не выполняются задачами L молча.

| Вариант | Игрок и гарантия | Инженерная цена, предварительно |
|---|---|---|
| **L — локальный UTC, пилот** | Прогресс и Claim offline; retry/restart защищены на одном устройстве. Клиентские часы/два устройства глобально не защищены | 3–5 инженерных дней на policy, receipts, journal и recovery; UI/цикл/неделя/аналитика отдельно |
| H — серверное время + локальная квота | Надёжная дата при связи; после cold offline дата либо неизвестна, либо недоверенная. Два независимых устройства ещё могут получать повтор | Дополнительно2–3 дня и сервис времени; проблему global claim оставляет |
| S — серверная дата и атомарный журнал выдач | Квота по владельцу на всех устройствах; новые earned/Claim требуют серверного подтверждения | Дополнительно8–15 дней на backend, клиент, конфликт/кошелёк и интеграционные проверки; серверная проверка gameplay шире этого диапазона |

Диапазоны — оценка объёма одного инженера, не календарное обещание. Рекомендация: L для ограниченного измерительного пилота после явного принятия рисков; если требуется строгая квота уже в первом выпуске — S вместо L. H полезен как clock-provider, но сам по себе не закрывает требование двух устройств. Правки Daily/W1 не входят в L.

## Точное правило L

- `policyVersion=local_utc_v1`. День `[00:00 UTC, следующие00:00 UTC)`. Неделя `[понедельник00:00 UTC, следующий понедельник00:00 UTC)`. `dayId=yyyy-MM-dd`, `weekId=UTC-дата понедельника`; вычисление независимо от культуры/номера недели ISO-года.
- На экране: локализованная дата/остаток и «Обновление в00:00 UTC»; в Москве это03:00. Изменение часового пояса меняет подпись локального времени, не идентификатор периода. DST не меняет сутки/неделю UTC.
- Дата берётся при первом durable commit qualifying Win. Смена даты во время игры относит результат к дате сохранённой победы, не запуска уровня. Первый durable receipt фиксирует дату; его replay/поздний показ/Claim сохраняют её.
- Если запись результата не состоялась, earned ещё нет. Повтор сохранения после полуночи получает новую дату; UI до успеха сообщает «Сохраняем результат». Показ Win сам по себе не доказательство durable зачёта.
- `cycleId` монотонный внутри owner+feature epoch, `step=1..7`. Общий `lastCreditedDay` действует через границу цикла: два шага одной даты невозможны. При пропуске сохраняется следующий шаг. День7 помечает completed; следующий cycle создаётся на первой более поздней дате с qualifying Win. Claim никак не управляет rollover.
- Weekly считает уникальные `attemptId` в своей неделе и множество дат. Зачтённая попытка может менять оба прогресса. Дубликат callback меняет ни один. После rollover earned старой недели остаётся, незавершённые счётчики хранятся только как краткая история результата. Late presentation не продлевает срок.
- Для L durable commit уже содержит progress/entitlements: отдельная сетевая синхронизация не пересчитывает дату. Выбранный cloud snapshot переносит подтверждённые IDs; загруженные сырые события прошлой недели не превращаются в новые победы текущей.
- Отсутствие сети не препятствует прогрессу/Claim L; Home пишет «Без сети · сохранено на устройстве». Нет профиля/идёт конфликт/сохранение недоступно — карточка читает snapshot, изменение ждёт разрешения; основная игра следует существующей политике профиля.

Граница других систем видна в подробностях: «Активности обновляются в00:00 UTC; задания — в полночь устройства». W1 сохраняет UTC **первого подтверждения рекорда**, а активность — дату **сохранённой победы**. Поздний рекорд может выдать W1 на следующую дату; это явное различие источников, а не повод пересчитать цикл задним числом.

## Clock anomalies и recovery L

`maxObservedUtcDay` и `lastCreditedDay` сохраняются. При возврате часов на уже использованную дату новый шаг не появляется; earned можно забрать. При времени ниже high-water новые периодические зачёты приостановлены: «Проверь дату устройства», ранее earned доступны. После выхода за high-water зачёт возобновляется. Прогресс недели старой даты не открывается повторно.

Скачок вперёд на новую дату между запусками L не может отличить от настоящего перерыва; новая дата может дать шаг и сдвинуть high-water. Возврат правильных часов затем способен временно заблокировать зачёт. Это реальный риск L. Самостоятельный сброс high-water при каждом входе нарушил бы квоту. Исправление ошибочного будущего high-water требует диагностики и отдельной явной коррекции профиля с сохранением earned/claimed ID; автоматический доверенный recovery относится к S. Внутри процесса для countdown использовать монотонное время, при resume перечитывать policy; таймер UI не создаёт entitlement.

## Данные и границы транзакций

Предлагаемые типы/API новые, сигнатуры согласует P3-00:

```text
ActivityWinReceipt: owner, profileEpoch, attemptId, levelProgressKey,
  stars, mode, committedUtc, dayId, weekId, policyVersion
ReturnActivityState: schemaVersion, featureEpoch, policyVersion,
  cycleId, nextStep, lastCreditedDay, maxObservedUtcDay,
  currentWeek(instanceId, templateVersion, wins, winDayIds), rewards
ActivityReward: rewardId, kind, cycleOrWeekId, step, earnedDay,
  configVersion, coins, gems, state(available/claimed), claimedReceipt
ActivityRewardSnapshot: profileId, generation, owner, rewardId,
  configVersion, coins, gems, originLabel, state
Claim(snapshot): claimed(receipt) | alreadyClaimed | staleContext |
  unavailable | saveFailed | syncRequired
```

`attemptId` выделяется на начале настоящей попытки и сохраняется owner-scoped technical transaction; revive сохраняет ID, Restart/Next создают новый. Runtime generation предотвращает поздний finish старой сцены. Новый `qualifying Win` hook вызывается **внутри** транзакции результата, без вложенного `ExecuteTransaction`: best/XP, receipt, cycle/week progress, earned и durable outbox аналитики становятся согласованными. После commit публикуется immutable snapshot. Служебный completion guard проверяет mode и реальный результат, не только публичный `CompleteLevel` с произвольными stars.

Claim: проверить owner/profile/generation/ID/суммы по хранимому entitlement; транзакционно добавить валюты, записать claimed receipt и journal, затем уведомить баланс. Payload UI не задаёт сумму. Ошибка до записи оставляет available, неопределённый результат перечитывается по тому же ID. Повтор Claim уже полученного возвращает прежнюю квитанцию с `newGrant=false`. Ошибка показа/ACK сохраняет выплату и повторяет только квитанцию.

IDs: `owner/featureEpoch/cycle/<cycleId>/day/<step>` и `owner/featureEpoch/week/<weekId>`. ConfigVersion хранит состав, но смена версии не создаёт второй rewardId той же недели. DEV namespace отдельный; guest использует устойчивый локальный owner GUID, после linking его история получает одноразовый mapping. Существующий аккаунт на другом устройстве требует штатного разрешения cloud conflict до мутаций. Смена account/profile полностью инвалидирует snapshots и async callbacks.

Хранение: PlayerData переносит доменный прогресс и receipts; journal сохраняет локальные decisions/claim IDs независимо от выбранного cloud baseline. При старом cloud baseline journal не запускает повторное начисление. Если выбранный snapshot уже потерял ранее потраченную/полученную валюту, из одного reward journal нельзя восстановить весь кошелёк: автоматический replay дельт способен продублировать потраченные деньги. При расхождении остановить activity mutations, выполнить явное разрешение конфликта с подходящим snapshot; точный recovery зафиксировать тестом. Два независимых устройства с разными journal остаются вне гарантии L.

Очистка: earned без Claim сохраняются; claimed циклы сворачиваются в закрытый диапазон cycle IDs, claimed недели — диапазоны/исключения. Сырые run receipts удаляются только после закрытия периода, сохранения агрегата и невозможности повторно принять старый attempt. Текущая неделя/текущая попытка держат точный dedupe. Старая дата и epoch никогда не открывают reward заново. Предельный размер/миграцию проверяет P3-02; тихое удаление pending запрещено требованием сохранения заработанного.

## S: минимальный общий серверный контракт при строгой квоте

Кандидат реализации: Cloud Code + серверно записываемое состояние. Unity документирует server-time use cases, Protected Player Data и optimistic write locks: [use cases](https://docs.unity.com/en-us/cloud-code/scripts/use-cases/advanced-use-cases), [access classes](https://docs.unity.com/en-us/cloud-save/concepts/player-data), [write locks](https://docs.unity.com/en-us/cloud-save/concepts/write-locks). Protected запрещает клиентскую запись; writeLock отклоняет обновление устаревшей версии. Это строительные блоки, готового atomic activity+wallet API в проекте пока нет.

1. `GetActivityState()` возвращает authenticated owner, serverUtc, policyVersion, revision, cycle/week/reward snapshots. Owner выводится из auth, не входного body.
2. `SubmitWin(commandId, attemptId, levelKey, stars, evidenceVersion)` назначает `acceptedAtUtc` сервером при первом durable принятии; receipt, quota, progress и entitlements фиксируются атомарно. Повтор command возвращает первоначальный результат. Правило при clock boundary — дата серверного принятия; клиентский timestamp только диагностический.
3. `ClaimActivityReward(commandId,rewardId,expectedRevision)` проверяет server entitlement, применяет валюту и claimed в одной authoritative транзакции, возвращает receipt+wallet revision. Повтор ответа/таймаут безопасны с тем же commandId.
4. Сериализовать конкурирующие команды одного owner; конфликт CAS вызывает read/recompute/retry. Инициализацию нового owner тоже защитить от двух одновременных create. Документация writeLock требует опускать lock при создании и допускает overwrite при null: наивный `load missing; save without lock` не доказательство атомарного первого Claim. P3-S1 обязан проверить/обеспечить create-if-absent либо single-writer/транзакционное хранилище. Финальный backend выбирается после этой проверки.
5. Один серверный журнал решает quota, но не весь кошелёк. Локальные `Money/Crystals`, покупки и full-snapshot CloudSave способны разойтись на устройствах. Для строгой end-to-end валюты нужны authoritative balance+spend либо серверный журнал всех валютных операций с дедупликацией. Перенос rewardId на сервер при локальном replay суммы не закрывает расход/rollback. Это обязательная зависимость P3-S2.

Серверное время само не доказывает Win: модифицированный клиент может прислать выдуманные stars. Первичный S защищает календарную квоту и выдачу; строгая проверка самого gameplay требует server-issued attempt/evidence validation и отдельной модели доверия. Эту границу обозначать в приёмке, а не называть всю игру защищённой от читов.

**Offline S:** обычная игра продолжается, qualifying результата UI показывает «Ожидает подтверждения». Outbox отправляется при связи; все впервые принятые в один UTC-день результаты дают максимум один день цикла, weekly получает принятые победы этого периода. Клиент не обещает восстановление пропущенных offline-дней. Старый уже принятый сервером receipt сохраняет свою исходную дату при retry; впервые принятая после окончания недели победа относится к новой неделе. Earned серверные награды без срока, Claim требует связи. Countdown без свежего clock anchor помечается как приблизительный/ожидающий синхронизации. Это сознательная продуктовая цена простого строгого режима.

Операционная оценка S: при условных12500 DAU, 2 входах/день, 5 Win/день, 1 дневном Claim и1/7 недельного Claim получаем примерно `12500*(2+5+1+1/7)=101786` вызовов/день, `3,05 млн/30 дней`, без повторов. Чтения/записи хранилища считаются отдельно: обычно ≥1 read+1 conditional write на mutation, плюс конфликтные retries. Поддержка: мониторинг latency/errors/двойных ID, бюджет запросов, версия конфигурации, clock boundary, восстановление outbox и миграций. Денежная цена требует фактического тарифа/проекта и профиля нагрузки; нулевая стоимость не заложена.

## Совместимость и переход

Общий интерфейс времени можно дать Daily/W1, сохранив их разные семантики. Общий backend quota может хранить отдельные namespaces `daily_set`, `weekly_record_xp`, `return_day`, `return_week`; совпадение UTC-даты не объединяет выплаты.

Миграция Daily local в UTC — отдельное решение: законченные pending-награды остаются с прежним SetId/суммой, старая активная дата закрывается по утверждённой boundary, новый набор получает новую policyVersion без повторной выдачи уже заработанного. W1 при переходе на server acceptance сохраняет старые0/5 решения как legacy, новые принимает через общую квоту. Точное время перехода, grandfathering текущего дня и import локальных earned требуют согласования владельцев. L и S нельзя переключать по наличию сети: иначе offline-клиент обходит строгую квоту.

Минимальная приёмка:23:59:59/00:00 UTC, воскресенье/понедельник, переход года, DST/смена timezone, повтор Win/Claim, шаг7+повтор в тот же день, пропуск месяца, поздний result/record, два available призa, убийство до/после commit/response/ACK, save failure, old cloud, смена аккаунта, offline cold start/reconnect. L фиксирует доказанные локальные гарантии и известный multi-device риск; S требует реальных конкурентных запросов двух клиентов и доказательства единого wallet. Парные DEV/Tools используют один production runner.
