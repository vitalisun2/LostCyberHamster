## Реклама и возвраты

- Rewarded: 11 показов/завершений/сохранённых наград, из них Win9 и Revive2. Ещё одно продолжение оплачено кристаллом. В конкретных попытках успешное продолжение оставалось одно.
- Win: 11 показов предложения, 9 выборов =81,8%; выплаты 17,39,30,43,36,39,33,30,42 =309 монет. Все девять равны `floor(валовая добыча своей победной попытки / 2)`. Это 8,1% всего дохода монет; исходная добыча выплачивается отдельно.
- Пользователь подтвердил, что охотно выбирал эту кнопку. Сигнал поддерживает полезность Win-бонуса для него; обычную аудиторию и реальные рекламные креативы не измеряет.
- Revive: 42 offer-события, два rewarded, один расход кристалла. Число offer-событий не равно уникальным людям или самостоятельным сессиям; повторные намеренные попытки влияют на выбор продолжения.
- Конфигурация APK: `ads_test_mode=true`, `purchases_enabled=false`, `interstitial_enabled=false`. Отсутствие принудительной рекламы ожидаемо. Реальную выручку/eCPM/IAP-конверсию по этим событиям оценить нельзя.
- Первый день возвратной активности забран: +10 монет. На конце return_days=1, UTC-дата всё ещё 10.09. Пять Daily Claim возможны из-за локальной полуночи и ротации набора; это не два отдельных визита.
- D1/D7/D30 и влияние на прибыль по одному разработчику и одному процессу не оцениваются.

## Дефект наблюдаемости и пересчёт

`EconomyTelemetry.cs:137–143` копит `_pending` по resource/source. Завершение попытки (:182–190) не фиксирует накопления отдельно, новая попытка (:162–174) меняет `_collectionRun`. `Transaction:127` может приписать весь массив последнему забегу. Проверка целостности общих checkpoint этого не обнаруживает.

Доказательство: файл `ac42bb33a109880ff44532fd16e893168156a8ee7de23acd80d3b5c4ef149ec5.jsonl:1`, event `4dcdeb3fb2d64bb4809b63b0055c10d8:224`: +170 монет отнесены к победе `a1a6ba73051d4f0b99e7833754dd53db`. По границам предыдущие проигрыши дали 25+29+55, эта победа61; сумма170.

Применённый пересчёт для каждой валюты: `run_finished.after − run_started.before − сумма отдельных неигровых дельт между sequence начала и конца`. Покупки с отрицательной дельтой добавляются обратно к валовой добыче. Ambient checkpoint/flows повторно не суммируются. Результат по всем попыткам совпал с общей игровой добычей2494/30; общий кошелёк также сошёлся. Разложение конкретной попытки на pickup/jump/bonus из объединённых flows восстановить нельзя; общая разбивка по источникам сохранена.

Маркеры для быстрого поиска в архиве: Level2 — session:122; shield — :129; Level3 — :767; Electric — :774; все XP — `economy_transaction` с `xp_delta>0`. Session выше. Исходные ссылки каждой операции есть в результате штатного `summarize.py` (`file`, `line`, `event_id`).

## Рекомендации и следующий прогон

1. Согласовать правило сохранения валют при Win/Lose/Replay. Ожидание пользователя и текущий код расходятся; менять цены и выпадение до решения преждевременно.
2. XP оставить текущим для следующего сравнения: 27–31 за первую победу и разовые квестовые выдачи подтвердились. Накопленная сумма и отдельная награда должны различаться при обсуждении UI.
3. Win rewarded оставить в текущем виде для следующего прогона: пользовательский отклик положительный, формула проверена. Запас монет и будущее использование кристаллов проверить при иной стратегии.
4. Исправление привязки игровой добычи к run_id — отдельная небольшая техническая задача. До неё применять пересчёт по границам, сохраняя общие источники отдельно.
5. Следующий стиль игры, предложенный пользователем: стремиться пройти дальше; принимать победу с1–2звёздами; использовать подходящие rewarded/продолжения/пополнения энергии и ульты, открывать и применять возможности. Тратить по потребности, а не опустошать кошелёк искусственно. При желании взять скин учесть отдельное открытие за DP.
6. Отдельно измерять первое прохождение уникальных уровней и последующий обязательный добор до64/66для следующей локации. Рестарты ради идеала до этого порога исключить из такого сценария. Для полного времени с нуля нужен отдельный новый профиль; продолжение текущего тоже полезно, но начинается с566XP/2893монет/29кристаллов.
7. Порог64/66уже требует почти полного освоения города. Предложение пользователя «подтюнить количество ... открытий» предварительно понято как число звёзд для доступа; конкретный новый порог не согласован. Сначала замер времени на добор; сохранять отдельно время, звёзды, повторы, XP, валюты, расходы и добровольные показы.
8. Новый прогон отделить по профилю/периоду/версии баланса. Длительность календарная и активная, теоретические цели и фактическая выручка — разные показатели. Для выводов о массовом удержании нужны другие игроки.
