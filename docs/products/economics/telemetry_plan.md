# Статистика Android-плейтестов — минимальный план

Дата: 2026-09-10. Статус: T1–T3 реализованы; desktop-проверки T4 пройдены, Android-приёмка ожидается. [Отчёт](telemetry_implementation.md).

## Результат

Пользователь играет на телефоне. История поступает в общую папку. Агент по запросу читает JSON, объясняет источники XP, доходы/расходы и скорость развития, предлагает точечную настройку баланса.

Основа: [готовое исследование в ChatGPT](https://chatgpt.com/share/6aa2f0fa-9e0c-83eb-bd28-4e009677829c), [текущая экономика](README.md), [доставка Android-логов](../../android_ngrok_device_logging.md). Повторный аудит экономики для планирования не проводился. Перед реализацией проверяются только затронутые контракты и изменения после исследования.

Пользователь выбрал необходимый минимум: структурированные файлы для агентов, существующий транспорт и короткий разбор по запросу. UGS-отчётность, графический интерфейс, Remote Config и Diagnostics — отдельные последующие этапы. Текущий этап покрывает собственные тестовые прогоны.

## T1 — Записывать фактическую историю игры

**Результат:** `economy_events.jsonl` в данных приложения; одна строка — один JSON события. Сбор включён явно в тестовой Android-сборке.

**Минимальный контракт:**

- Общие поля: `schema_version`, `event_id`, UTC-время, порядковый номер записи, ID профиля и поколения сохранения, `session_id`, версия сборки, `balance_version`; `run_id` при связи с попыткой. Сброс профиля создаёт новое поколение.
- `session_started` и снимок профиля: уровень персонажа, остаток XP, монеты, кристаллы, свободные очки развития, открытые/улучшенные способности и скины, выбранное снаряжение, прогресс кампании.
- `run_started` / `run_finished`: полный адрес уровня, первая/повторная попытка, победа/окончательное поражение/выход, звёзды и их улучшение, активные секунды без пауз/рекламы, снимки до/после, доход и расход раздельно. Возрождение продолжает ту же попытку. Незавершённая попытка после перезапуска помечается прерванной с известной полнотой данных.
- `economy_transaction`: стабильный ID операции, источник/причина, фактические изменения ресурсов, состояние до/после, связь с забегом, квестом, рекламой или покупкой. XP хранить как начисленную сумму вместе с уровнем и остатком до/после.
- Существующие события квестов, возвращаемых активностей и рекламы направить также в локальный журнал: начало/завершение/получение награды, предложение/старт/результат показа и placement. Реальную покупку отличать от тестовой выдачи; использовать существующий подтверждённый результат и ID покупки.

Охват начислений: обучение, первая победа/новые звёзды, Daily/Story/weekly, возвращаемые активности, rewarded и покупки. Охват расходов: магазин/обмен, энергия/ульта, возрождение, скины, открытия/улучшения. DEV-начисления явно помечать для исключения из обычного прогона.

Отдельные награды/покупки записывать после успешного сохранения по фактическому результату операции. Добычу забега суммировать по источникам между существующими checkpoint, сохраняя раздельные доходы и расходы. Промежуточные суммы считать неподтверждёнными до checkpoint. Финал забега и снимки — контрольные итоги; повторно суммировать их как начисления нельзя.

При старте сверять последний подтверждённый снимок с сохранением. Разрыв между сохранением и журналом фиксировать как неизвестное изменение. Это позволяет честно обозначать неполный прогон после аварийного закрытия, сохраняя существующий механизм сохранений.

**Точки интеграции:** `Assets/Scripts/Analytics/`, `Diagnostics/`, `GameManagement/PlayerProgress/`, `GameManagement/Persistence/`, `System/LevelManagement/LevelManager.cs`; конкретные producer-точки в `SharedCore/Meta/`, `Ads/`, `Leaderboard/`. Пути относительно `LostCyberHamster/`. Перед правкой выбрать минимальные точки по текущим контрактам; таблицу источник → точка записи сохранить в отчёте реализации.

**Приёмка:** все перечисленные источники имеют запись или явно обозначенный статус «функция выключена»; один подтверждённый результат даёт одно начисление в анализе. Повышение уровня, повторный callback и отклонённая операция отражаются корректно. Игровые награды и порядок сохранений сохраняют прежнее поведение.

## T2 — Доставлять и сохранять журнал

**Зависимость:** T1.

**Результат:** существующий канал Android → ngrok → collector → Dropbox доставляет отдельный JSONL без обрезки хвостом `diagnostic_log.txt`.

- Расширить существующие `DeviceLogUploader` / `DeviceLogUploadRunner` / `DeviceLogReporter` и `tools/device-log-collector/server.js` в пределах передачи экономического файла.
- Отправлять ограниченные по размеру пакеты целых строк: после завершённой попытки, по существующему таймеру и lifecycle. Полученные в меню награды также доходят без следующего забега.
- Сохранять неподтверждённые пакеты на телефоне между перезапусками. Повторять доставку после восстановления сети/receiver. Удалять пакет из очереди после подтверждения записи collector-ом. Повторы распознавать по `event_id`.
- Задать явный предел локальной очереди. При переполнении сохранять маркер потери и границу доступной истории, чтобы агент отмечал неполный период.
- Collector автоматически сохраняет принятые экономические пакеты в соседний архив `LostCyberHamster_Playtests/android`, вне дерева текущей 72-часовой очистки. К существующим диагностическим логам применяется прежняя политика хранения.
- В архиве сохранять метаданные профиля, сессии, сборки и версии баланса. Использовать существующее разделение тестового и production upload.

**Приёмка:** данные одной сессии доступны в синхронизированной папке; повторная отправка не удваивает итог. После офлайна и перезапуска очередь доходит. Архив остаётся после очистки диагностических логов. Ошибка доставки видна как ожидающая очередь или неполный период.

**Условие доставки:** телефон и receiver получают сеть; receiver включён, Docker stack и Dropbox работают. До этого журнал ожидает отправки на телефоне в пределах очереди.

## T3 — Подготовить JSON для ответа агента

**Зависимость:** T1–T2.

**Результат:** небольшой скрипт в `tools/economy/` читает архив, выбирает профиль/поколение, период и версию баланса; создаёт `summary.json`. Сырые JSONL остаются источником деталей.

Скрипт объединяет повторные загрузки по `event_id`, считает операции по стабильному ID и сохраняет конфликты/пропуски в качестве данных. Сессии сортируются с учётом последовательности; смена часов отмечается. DEV и обычная игра разделены.

Минимальное содержание `summary.json`:

- Происхождение: выбранный профиль, период, версии, исходные файлы, время последнего события и последней загрузки, полнота/пропуски/конфликты.
- Забеги: активные минуты, попытки, победы/поражения/выходы по уровням; прерванные попытки отдельно.
- Прогрессия: XP по источникам, начисленный XP за активную минуту, минуты и попытки до повышения/открытия/улучшения. Стартовые одноразовые награды и дальнейшая игра разделены.
- Экономика: доходы и расходы по причинам, начальные/конечные остатки, расхождения с контрольными снимками.
- Возвраты и монетизация: даты/интервалы игровых сессий, квесты и полученные награды, предложения/завершённые показы по placement, подтверждённые покупки при доступности функции.

Рядом — короткая инструкция агенту: команда запуска, путь к архиву и правило ответа «измеренные факты; соответствие текущим правилам/целевому темпу; гипотеза; предлагаемая настройка». Каждое численное заключение имеет период, объём прогона и ссылку на исходные записи. Изменение баланса обсуждается с пользователем отдельно.

Локальный агент читает синхронизированную папку. Агент в ChatGPT/Work получает `summary.json` и нужные JSONL через прикреплённые файлы либо уже доступный ему источник. Доступ одного агента к локальной папке не означает доступ всех чатов.

**Приёмка:** повторный запуск на тех же данных даёт те же показатели; дубли не меняют суммы; неполные данные видны. По вопросу «откуда сегодня почти 100 XP?» агент называет конкретные операции. По одному тестовому профилю выводы относятся к его траектории; общие D1/D7 и выручка требуют соответствующих данных игроков и сервисов.

## T4 — Проверить полный путь на Android

**Зависимость:** T1–T3.

**Результат:** тестовый APK, один известный прогон, архив и `summary.json`, сверенные с фактическим сохранением.

1. Проверки изменённых C# и минимальный запуск Editor по правилам проекта; узкие проверки журналирования, повторов, XP rollover и восстановления очереди. Для скрипта — небольшой набор с дублем, пропуском и доходом/расходом в одном забеге.
2. Собрать тестовый Android через штатный build entrypoint. Игровую приёмку на телефоне выполняет пользователь; агент готовит короткий сценарий и разбирает доставленные данные.
3. Сценарий: обучение/новый профиль, первая победа, повтор без улучшения, Claim квеста, покупка/улучшение, поражение/выход, пауза, игра без сети и перезапуск, возврат сети. Rewarded/IAP проверять по доступному провайдеру с явной отметкой тестовых результатов.
4. Сверить начисления, расходы, уровни, остатки, попытки и активное время. Проверить доставку последних операций меню, повтор загрузки, разделение профилей/версий и сохранность архива.
5. Зафиксировать фактические проверки и оставшуюся ручную приёмку в `telemetry_implementation.md`; добавить команду анализа в `docs/rules/agent_tools.md` и обновить owner-документ доставки.

**Готово:** после игры и успешной синхронизации агент по файлам восстанавливает подтверждённые начисления/траты и темп прогрессии, указывает свежесть и полноту данных, отделяет ошибку расчёта от предложения по балансу. До выполнения Android-сценария статус — «реализовано, доставка/приёмка на телефоне ожидается».
