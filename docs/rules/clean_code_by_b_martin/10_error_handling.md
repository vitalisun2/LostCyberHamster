# Обработка ошибок

## Концепция

Обработка ошибок не должна ломать чтение нормального сценария. Ошибка должна нести контекст, а вызывающая сторона должна понимать, что делать дальше. Возврат `null` и кодов ошибок часто размывает контракт и заставляет проверять одно и то же везде.

## Когда читать

- Добавляются guard-проверки, исключения, fallback или `null`.
- Метод возвращает `bool`/код ошибки вместо результата.
- Обработка ошибок смешана с основной логикой.

## Правила

- Нормальный путь выполнения должен читаться отдельно от обработки ошибок.
- Не возвращай `null`, если можно вернуть пустую коллекцию, `Optional`-подобный тип, `Try...`-паттерн или бросить осмысленное исключение.
- Не передавай `null` как штатный сигнал.
- Исключение должно содержать контекст: что искали, какой id, какой режим.
- В Unity-коде исключения не должны заменять обычную игровую ветку; используй их для нарушенных контрактов и инфраструктурных сбоев.

## Пример

Плохо: результат и ошибка неразличимы без внешних догадок.

```csharp
private LevelConfig LoadLevel(string levelId)
{
    if (!_levels.TryGetValue(levelId, out LevelConfig config))
        return null;

    return config;
}
```

Лучше для штатного отсутствия:

```csharp
private bool TryLoadLevel(string levelId, out LevelConfig config)
{
    return _levels.TryGetValue(levelId, out config);
}
```

Лучше для нарушенного инварианта:

```csharp
private LevelConfig GetRequiredLevel(string levelId)
{
    if (!_levels.TryGetValue(levelId, out LevelConfig config))
        throw new InvalidOperationException($"Level config not found: {levelId}");

    return config;
}
```

## Правило для агента

Выбери один честный контракт: результат есть всегда, результата может не быть, или отсутствие результата является ошибкой. Не смешивай эти режимы в одном методе.
