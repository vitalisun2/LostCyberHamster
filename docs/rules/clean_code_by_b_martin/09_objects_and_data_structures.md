# Объекты и структуры данных

## Концепция

Объект скрывает данные и раскрывает поведение. Структура данных раскрывает данные и почти не содержит поведения. Оба подхода нормальны, но смешивание часто создает гибрид: поля торчат наружу, а логика размазана по вызывающему коду.

## Когда читать

- Добавляется DTO, config, save data, ScriptableObject.
- Код тянется через цепочку `a.B.C.D`.
- Поведение домена реализуется вне объекта, которому оно принадлежит.

## Правила

- DTO и конфиги могут быть простыми структурами данных.
- Domain object должен давать методы поведения, а не заставлять внешние классы менять его внутренности.
- Избегай "крушения поезда": длинных цепочек доступа к деталям.
- Не создавай гибрид, где все поля публичные, но часть логики случайно лежит внутри.
- Передавай намерение через метод, а не через набор внутренних частей объекта.

## Пример

Плохо: вызывающий код знает слишком много о внутренней структуре.

```csharp
if (bot.State.Movement.Roof.CurrentSegment.ExitGap.Width < minGap)
{
    bot.State.Movement.Roof.CurrentSegment.ExitGap.IsBlocked = true;
}
```

Лучше: объект раскрывает поведение на своем уровне.

```csharp
if (bot.RoofRun.HasUnsafeExitGap(minGap))
{
    bot.RoofRun.BlockCurrentExitGap();
}
```

DTO при этом допустим:

```csharp
public sealed class ObstacleConfig
{
    public string Id;
    public Vector2 Size;
    public float SpawnWeight;
}
```

## Правило для агента

Если код снаружи объекта принимает решения на основе его внутренних деталей, проверь: это действительно структура данных или поведение должно переехать ближе к данным?
