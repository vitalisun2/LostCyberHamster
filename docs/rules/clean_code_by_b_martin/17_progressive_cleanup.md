# Последовательная очистка

## Концепция

Сложный код редко становится чистым одним прыжком. Надежный путь: зафиксировать поведение, сделать минимальное работающее изменение, затем постепенно выделять имена, функции и классы, постоянно проверяя, что поведение не изменилось случайно.

## Когда читать

- Большой метод или класс страшно менять.
- Нужно улучшить старый алгоритм.
- Есть желание переписать с нуля.

## Правила

- Не переписывай без понимания текущего поведения.
- Сначала собери карту: входы, выходы, инварианты, побочные эффекты.
- Делай маленькие механические шаги: rename, extract method, remove duplication.
- После каждого смыслового шага проверяй поведение доступным способом.
- Если тестов нет, используй минимальные локальные проверки, логику чтения и ручной сценарий проекта.

## Пример процесса

1. Прочитать метод целиком и записать, что он делает.
2. Переименовать очевидно плохие локальные переменные.
3. Выделить один непротиворечивый блок в метод с точным именем.
4. Устранить один повтор.
5. Проверить, что внешнее поведение не поменялось.
6. Остановиться, когда код стал достаточно понятным для текущей задачи.

## Антипример

```text
"Метод плохой, поэтому я сразу заменю его новой архитектурой"
```

Это рискованно: новая архитектура может потерять скрытые граничные условия старого кода.

## Правило для агента

Рефакторинг должен идти через сохранение смысла, а не через стирание непонятного. Если смысл не восстановлен, правка преждевременна.
