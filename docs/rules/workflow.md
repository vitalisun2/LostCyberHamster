# Workflow

Ветки, `integration/unity-live`, worktree, жизненный цикл задачи, git-правила, отчётность.

## Структура репозитория

- Корень git: корневая директория репозитория
- Unity-проект: `LostCyberHamster/`
- Документация и планы: `docs/`
- Основной рабочий каталог: корневая директория репозитория, открытая в Unity Editor на локальной рабочей ветке `integration/unity-live`
- Worktree задач: `.worktrees/<slug>/` (игнорируется git, используется только по явному запросу на отдельную ветку/worktree)

## Типы задач

- **Аналитические:** анализ, исследование, аудит, ответы на вопросы. По умолчанию без отдельной ветки и worktree.
- **Исполнительные:** изменения кода, ассетов, настроек, тестов, документации. По умолчанию выполняются прямо в `integration/unity-live`.

**По умолчанию:** любое исполнительное изменение — включая правку документации, одного файла, одной строки — делается в `integration/unity-live`.

**Отдельная ветка + worktree:** только по явному запросу пользователя. Формулировки «в отдельной ветке» и «в отдельном worktree» считаются эквивалентными: агент создаёт отдельную ветку и отдельный worktree под неё.

**По умолчанию:** commit делать только по явному запросу пользователя (on demand). Компиляция и Unity-валидация — тоже по явному запросу пользователя. Для чистой документации compile step не требуется.

## Входное чтение перед планом и реализацией

Перед подготовкой плана реализации или рефакторинга и перед первой содержательной правкой кода агент обязан:

- выполнить входное чтение из `docs/rules/AGENTS.md`, включая временные правила текущего этапа;
- если задача затрагивает код, рефакторинг или code review, выбрать 2-5 релевантных тем из `docs/rules/clean_code_by_b_martin/README.md` и прочитать их до составления плана;
- использовать Clean Code только как вспомогательный фильтр внутри уже принятых project rules; при конфликте приоритет у `docs/rules/*.md`, активного плана и явного запроса пользователя;
- если релевантная рекомендация Clean Code существенно расходится с проектным правилом, кратко сообщить пользователю о расхождении при представлении анализа, плана или результата;
- если после анализа или чернового плана scope изменился, уточнить набор тем до первого содержательного изменения.

## Именование веток

- Основная рабочая ветка по умолчанию: `integration/unity-live`.
- Ниже по тексту `unity-live` — краткое имя для ветки `integration/unity-live`.
- Для изолированного workflow: префикс `task/<slug>`. Примеры: `task/fix-switchlane-safety`, `task/add-levelkey-struct`.

Не использовать префиксы агентов (`codex/`, `claude/`, `copilot/`).

## Стандартный workflow (`integration/unity-live`)

Стандартный workflow ниже предполагает, что это входное чтение уже выполнено.

### Фаза 1 — реализация (автономная)

```
1. Убедиться, что основной каталог находится на ветке integration/unity-live
2. Реализовать изменения прямо в основном каталоге
3. Проверить затронутые файлы: summary методов и комментарии логических единиц (см. code_conventions.md), если правился код
4. Провалидировать только релевантное и только по явному запросу пользователя:
    a. Документация и планы без изменений Unity-проекта -> compile step не требуется
    b. Изменения .cs -> при явном запросе: recompile_scripts + запуск релевантных существующих EditMode/PlayMode тестов, если они уже есть
    c. Изменения ассетов, настроек, build config -> при явном запросе: релевантная Unity/build validation, если доступна
5. Если пользователь явно запросил commit: после релевантной валидации создать commit в integration/unity-live.
6. Перед передачей на ревью при необходимости запушить integration/unity-live и зафиксировать hash последнего commit (если commit был создан)
```

### Фаза 2 — проверка в Unity + code review

`integration/unity-live` — рабочая и ревью-ветка по умолчанию. Пользователь делает ручную проверку в Unity Editor прямо в основном каталоге на этой ветке.

Обязательное правило: задача не считается готовой к пользовательскому ревью, пока не завершены релевантные правки и валидация. Наличие commit перед ревью зависит от явного запроса пользователя.

```
7.  Сообщить пользователю:
    a. Задача готова к ревью на integration/unity-live.
    b. Что именно провалидировал агент локально.
    c. Что ручную проверку в Unity и автопрогон выполняет пользователь.
    d. Ветка и хэш последнего commit (если commit был создан).
8.  СТОП и ждать явного одобрения пользователя. Не продолжать без команды.
9.  Если пользователь запросил доработки:
    a. Внести правки в integration/unity-live.
    b. Commit делать только по явному запросу пользователя.
    c. Повторить с шага 3.
```

**Агент НЕ ИМЕЕТ ПРАВА переходить к фазе 3 без явного одобрения пользователя.** Никакие обстоятельства (простота изменений, «только документация», уверенность в корректности) не являются основанием пропустить code review.

### Фаза 3 — merge (после одобрения)

```
10. Смержить integration/unity-live в main
11. Запушить main и, если ветка публикуется на remote, актуальный integration/unity-live
12. Проверить, что main и integration/unity-live указывают на один и тот же commit
```

## Workflow с отдельной веткой/worktree (только по явному запросу)

Все worktree создаются в `.worktrees/<slug>`.

```
1. Создать worktree + ветку task/<slug> от integration/unity-live
2. Реализовать изменения внутри worktree
3. Проверить затронутые файлы и провалидировать только релевантное по тем же правилам, что и для integration/unity-live
4. Если пользователь явно запросил commit: после релевантной валидации создать commit в task/<slug>
5. При необходимости запушить task/<slug>
6. Когда изолированная реализация готова, захватить unity-live lock (см. «Unity-live lock»), влить task/<slug> обратно в integration/unity-live и перейти к стандартному workflow с фазы 2
7. После одобрения пользователя смерджить integration/unity-live в main
8. После завершения merge удалить worktree, локальную ветку и remote-ветку, если они были созданы
```

Если пользователь внёс ручные правки прямо в `integration/unity-live` во время ревью отдельной ветки, агент обязан синхронизировать эти commit(s) обратно в активную `task/<slug>` до следующего изолированного цикла (`cherry-pick` предпочтителен, `merge` допустим при безопасном и понятном результате).

### Unity working branch

- Unity Editor открыт на основном каталоге на ветке `integration/unity-live`, не на `main`.
- Основной каталог для ручной проверки пользователя в Unity — локальная ветка `integration/unity-live`.
- `main` не использовать как черновую ветку.
- После завершения задачи `main` и `integration/unity-live` обязаны быть идентичны: один и тот же commit. Если ветки публикуются на remote, на remote они тоже должны быть синхронизированы.
- Если пользователь на ручной проверке нашёл проблему — доработка по умолчанию продолжается в `integration/unity-live`. Если задача идёт в отдельном worktree по явному запросу пользователя, правки вносятся в `task/<slug>` с последующей синхронизацией обратно в `integration/unity-live`.

### Unity-live lock

`integration/unity-live` и Unity Editor — разделяемый ресурс только для параллельных и изолированных workflow. При обычной последовательной работе прямо в основном каталоге на `integration/unity-live` lock не нужен.

**Механизм:** атомарное создание директории `.worktrees/.integration-lock/`.

**Захват:**
1. `mkdir .worktrees/.integration-lock/`
   - Успех → записать файл `.worktrees/.integration-lock/owner.json` с содержимым: `{"task": "<slug|unity-live>", "phase": "publish|review|merging", "timestamp": "<ISO 8601>"}`.
    - Неудача (директория существует) → прочитать `owner.json`, сообщить пользователю «unity-live занята задачей X (фаза Y), жду», повторять попытку каждые 30 секунд.
2. Выполнить публикацию из `task/<slug>` в `integration/unity-live`, ревью или merge, если workflow требует изоляции/параллелизма.
3. Удалить `.worktrees/.integration-lock/` (release).

**Stale lock:** stale lock detection отключён — lock может удерживаться на время code review (минуты–часы). Если агент видит занятый lock, он сообщает пользователю и ждёт. Пользователь решает, протух lock или нет.



Тестовые уровни и скорости автопрогона — справочный материал для ручной проверки пользователя и для случаев, когда пользователь явно просит агента запустить прогон. Это больше не обязательная часть стандартного workflow агента.

### Критерий завершения задачи (обязательно)

Задача считается завершённой только при выполнении **двух** условий одновременно:

- **Tech Done:** изменения внесены и валидация пройдена.
- **Workflow Done:** git-цикл доведён до конца по выбранному workflow.

Для стандартного workflow задача не считается завершённой, пока после явного одобрения пользователя merge `integration/unity-live -> main` не выполнен. Если ветки публикуются на remote, обязательна публикация всех затронутых веток выбранного workflow.

Дополнительно обязателен **Learning Review Done**:

- Выполнен Efficiency Review по `docs/rules/agent_efficiency_playbook.md`.
- Новые reusable lessons добавлены в playbook как `incubating` или перенесены в файл-владелец темы с `promoted`-ссылкой.
- Если новых lessons нет, пустые записи не добавлены, а это явно указано в отчёте.

Для задачи в отдельном worktree закрытие допустимо только после всех пунктов:

1. `git status --short` пуст на текущей ветке.
2. Если пользователь запрашивал commit — изменения закоммичены в `task/<slug>`.
3. Изменения перенесены из `task/<slug>` в `integration/unity-live`.
4. После одобрения пользователя выполнен merge `integration/unity-live -> main`.
5. Если затронут remote, нужные ветки запушены.
6. Worktree и временная ветка удалены.

До выполнения этого чеклиста агент не имеет права объявлять задачу завершённой.

## Параллельное выполнение

Параллельность по умолчанию: параллелить, если нет причин не параллелить.

### Когда НЕ распараллеливать

- Задача мелкая или линейная.
- Подзадачи меняют одни и те же файлы.
- Координация дороже выигрыша по времени.

### Оркестратор

Для сложных задач основной агент:

1. Декомпозирует задачу на независимые подзадачи.
2. Разделяет по риску конфликтов: каждая подзадача — свой набор файлов.
3. Раздаёт подзадачи background-агентам с чётким scope и форматом результата.
4. Собирает результаты и синтезирует итог.

### Параллельная реализация

1. Оркестратор создаёт worktree + ветку только для действительно независимых подзадач или по явному запросу пользователя.
2. Каждый агент работает в своём worktree и валидирует независимо.
3. Подготовка `integration/unity-live` для ручной проверки пользователя — последовательно через unity-live lock.
4. Все завершённые изолированные задачи синхронизируются обратно в `integration/unity-live` и ожидают code review там.
5. После одобрения пользователем — merge `integration/unity-live` в `main`.
6. После завершения merge — удаление временных worktree и веток.

## Unity: правила владения файлами

Unity YAML-ассеты практически не мержатся. Один владелец на файл.

Высококонфликтные пути — всегда один владелец:
- `LostCyberHamster/Assets/AddressableAssetsData/`
- `LostCyberHamster/ProjectSettings/`
- `LostCyberHamster/Packages/manifest.json`, `packages-lock.json`
- `*.unity`, `*.prefab`, `*.asset`, `*.meta`

Если задача требует согласованных изменений в коде и контенте — вести в одном потоке.

## Lifecycle файлов задач в docs/Planning/in-progress/

Каждая исполнительная задача, требующая детального трекинга, может иметь файл-спек в `docs/Planning/in-progress/`.

**Когда создаётся:**
- При запуске задачи, если задача достаточно сложна чтобы её описать.
- Агент создаёт файл `docs/Planning/in-progress/<slug>.md` с описанием: что делать, какие файлы менять, паттерны тестов.

**Когда удаляется:**
- После одобрения пользователем и merge в `main`.
- Если использовался отдельный worktree, файл можно удалить в том же шаге, что завершает cleanup worktree и ветки.
- До одобрения файл остаётся — он часть артефакта для ревью.

**Сводный tracking-документ (`obstacle_interaction_coverage.md` и аналоги):**
- Статус задачи в roadmap-таблице обновляется при merge: `📋 В очереди` → `✅ Выполнено`.
- Ссылка на `<slug>.md` остаётся в таблице даже после удаления файла — как ссылка на историю (файла нет, но история в git).

## Git

- Коммитить только файлы текущей задачи.
- Коммит выполнять только по явному запросу пользователя.
- Push делать тогда, когда ветку нужно опубликовать для ревью, синхронизации между workflow или завершения merge-цикла.
- Не делать force-push.
- При ошибке push — остановиться и сообщить точную ошибку.

## Отчёт по завершении задачи

Всегда указывать:
- Тип задачи: аналитическая или исполнительная.
- Оставшиеся блокеры или ручные проверки.
- Если по ходу задачи обнаружено существенное расхождение между проектным правилом и релевантной рекомендацией Clean Code, кратко указать это в ответе: что применено в проекте и какая альтернатива была сознательно не выбрана.
- Подтверждение `Learning Review Done`: `agent_efficiency_playbook.md` дополнен, owner rules обновлены/promoted или новых lessons нет.

Для аналитической:
- Краткий итог находок.

Для исполнительной:
- Результат валидации и какие проверки запущены агентом.
- Что осталось на ручную проверку пользователя в Unity.
- Ветка. Если использовался отдельный worktree — дополнительно путь worktree и временная ветка.
- Хэш коммита (если commit был создан).
- Успешность push, если push выполнялся в выбранном workflow.
- Подтверждение `Tech Done` и `Workflow Done`.
- Подтверждение `Learning Review Done` (`promoted X / incubating Y / новых lessons нет`).
