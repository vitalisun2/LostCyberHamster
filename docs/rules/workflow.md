# Workflow

Ветки, worktree, жизненный цикл задачи, git-правила, отчётность.

## Структура репозитория

- Корень git: корневая директория репозитория
- Unity-проект: `LostCyberHamster/`
- Документация и планы: `docs/`
- Worktree задач: `.worktrees/<slug>/` (игнорируется git)
- Integration workspace: основной каталог репозитория, открытый в Unity Editor на локальной integration-ветке

## Типы задач

- **Аналитические:** анализ, исследование, аудит, ответы на вопросы. Без ветки и worktree.
- **Исполнительные:** изменения кода, ассетов, настроек, тестов, документации. Всегда в отдельной ветке.

**Без исключений:** любое исполнительное изменение — включая правку документации, одного файла, одной строки — проходит полный стандартный workflow с worktree, валидацией и code review. Сокращённых путей нет.

## Именование веток

Единый префикс: `task/<slug>`. Примеры: `task/fix-switchlane-safety`, `task/add-levelkey-struct`.

Не использовать префиксы агентов (`codex/`, `claude/`, `copilot/`).

## Стандартный workflow (worktree)

Все worktree создаются в `.worktrees/<slug>`.

### Фаза 1 — реализация (автономная)

```
1. Создать worktree + ветку task/<slug>
2. Реализовать изменения внутри worktree
3. Проверить затронутые файлы: summary методов и комментарии логических единиц (см. code_conventions.md)
4. Провалидировать:
   a. Компиляция (recompile_scripts)
   b. Прогнать все тестовые уровни (`invoke_run_all_test_levels.ps1`)
   c. Прочитать логи (STAB → BOT → ECO), убедиться в отсутствии регрессий
5. Закоммитить и запушить в task/<slug>
```

### Фаза 2 — проверка в Unity (автономная, кратковременный lock)

Integration-ветка — временный стенд для тестирования, не зона ожидания. Агент занимает её только на время проверки.

```
6.  Захватить integration lock (см. «Integration lock»)
7.  Синхронизировать integration-ветку от main
8.  Смержить task/<slug> в integration-ветку
9.  Проверить в Unity, прочитать логи
10. Если проверка не прошла:
    a. Откатить integration к main: git reset --hard main
    b. Освободить lock
    c. Доработать в worktree, повторить с шага 3
11. Если проверка прошла:
    a. Откатить integration к main: git reset --hard main
    b. Освободить lock
```

### СТОП — code review

```
12. Остановиться. Сообщить пользователю:
    — Задача task/<slug> готова к ревью.
    — Результат валидации и Unity-проверки.
    — Ветка, хэш коммита, путь worktree.
    Ждать явного одобрения пользователя. Не продолжать без команды.
13. (Опционально) Создать PR из task/<slug> в main для удобства ревью.
    PR используется только как артефакт для ревью — merge выполняется локально.
```

**Агент НЕ ИМЕЕТ ПРАВА переходить к фазе 3 без явного одобрения пользователя.** Никакие обстоятельства (простота изменений, «только документация», уверенность в корректности) не являются основанием пропустить code review.

### Фаза 3 — merge (после одобрения, кратковременный lock)

```
14. Захватить integration lock
15. Смержить task/<slug> в main
16. Запушить main
17. Обновить integration-ветку от main
18. Освободить integration lock
19. Удалить worktree, локальную ветку и remote-ветку
20. Закрыть PR, если был создан
```

### Unity integration branch

- Unity Editor открыт на основном каталоге, не на task-worktree.
- Основной каталог для Unity-проверок — локальная integration-ветка (например `integration/unity-live`).
- `main` не использовать как черновую ветку.
- Если проверка неуспешна — доработка в worktree; integration-ветка возвращается к чистому состоянию.

### Integration lock

Integration-ветка и Unity Editor — разделяемый ресурс. Lock захватывается **дважды за задачу, каждый раз кратковременно**: на фазе 2 (тестирование) и на фазе 3 (merge). Между ними lock свободен — другие агенты могут тестировать свои задачи.

**Механизм:** атомарное создание директории `.worktrees/.integration-lock/`.

**Захват:**
1. `mkdir .worktrees/.integration-lock/`
   - Успех → записать файл `.worktrees/.integration-lock/owner.json` с содержимым: `{"task": "<slug>", "phase": "testing|merging", "timestamp": "<ISO 8601>"}`.
   - Неудача (директория существует) → прочитать `owner.json`, сообщить пользователю «integration занята задачей X (фаза Y), жду», повторять попытку каждые 30 секунд.
2. Выполнить шаги текущей фазы.
3. Удалить `.worktrees/.integration-lock/` (release).

**Stale lock:** если timestamp в `owner.json` старше 15 минут — lock считается протухшим. Агент:
1. Сообщает пользователю: «lock задачи X протух (>15 мин), перехватываю».
2. Удаляет старый lock, создаёт свой.

**Принцип:** lock удерживается минуты, не часы. Никогда не держать lock во время ожидания code review.



| Уровень | Адрес | Что тестирует |
|---|---|---|
| test_threat_small_notalive_road_switchlane | `01_New_York/Morning/test_threat_small_notalive_road_switchlane` | Threat smallNotAliveRoad + SwitchLane |
| test_threat_small_notalive_road_jump | `01_New_York/Morning/test_threat_small_notalive_road_jump` | Threat smallNotAliveRoad + Jump |

При валидации прогонять **все** тестовые уровни из таблицы.

Дефолтная скорость: через `Tools` menu — `1.0` (интерактивный визуальный просмотр); через automation bridge — `4.0` (бот включён, применяется автоматически).

### Критерий завершения задачи (обязательно)

Задача считается завершённой только при выполнении **двух** условий одновременно:

- **Tech Done:** изменения внесены и валидация пройдена.
- **Workflow Done:** git-цикл доведён до конца по выбранному workflow.

Дополнительно обязателен **Promotion Check Done**:

- Проверены новые/обновлённые пункты в `ai_workflow_lessons.md`.
- Зрелые lessons перенесены в файл-владелец темы в `docs/rules/`.
- В `ai_workflow_lessons.md` выставлен статус (`incubating` или `promoted`) для новых/обновлённых lessons.

Для `task/refactoring` закрытие задачи допустимо только после всех пунктов:

1. `git status --short` пуст на текущей ветке.
2. Коммит создан в `task/refactoring`.
3. Push в `origin/task/refactoring` успешен.
4. Merge `task/refactoring -> main` выполнен.
5. Push `origin/main` успешен.

До выполнения этого чеклиста агент не имеет права объявлять задачу завершённой.

## Параллельное выполнение

Параллельность по умолчанию: параллелить, если нет причин не параллелить.

### Когда НЕ распараллеливать

- Задача мелкая или линейная.
- Подзадачи меняют одни и те же файлы.
- Координация дороже выигрыша по времени.

### Оркестратор

Для сложных задач основной агент:

1. Декомпозирует задачу на независимые подзадачи.
2. Разделяет по риску конфликтов: каждая подзадача — свой набор файлов.
3. Раздаёт подзадачи background-агентам с чётким scope и форматом результата.
4. Собирает результаты и синтезирует итог.

### Параллельная реализация

1. Оркестратор создаёт worktree + ветку для каждой подзадачи.
2. Каждый агент работает в своём worktree и валидирует независимо (фаза 1 — полностью параллельна).
3. Тестирование в Unity (фаза 2) — последовательно через integration lock, но каждый агент занимает lock только на время теста и сразу освобождает.
4. Все завершённые задачи ожидают code review (worktree и ветка сохраняются).
5. После одобрения пользователем — merge в main последовательно, по одной (фаза 3, через integration lock).
6. После каждого merge — удаление worktree и ветки.

## Unity: правила владения файлами

Unity YAML-ассеты практически не мержатся. Один владелец на файл.

Высококонфликтные пути — всегда один владелец:
- `LostCyberHamster/Assets/AddressableAssetsData/`
- `LostCyberHamster/ProjectSettings/`
- `LostCyberHamster/Packages/manifest.json`, `packages-lock.json`
- `*.unity`, `*.prefab`, `*.asset`, `*.meta`

Если задача требует согласованных изменений в коде и контенте — вести в одном потоке.

## Lifecycle файлов задач в docs/Planning/in-progress/

Каждая исполнительная задача, требующая детального трекинга, может иметь файл-спек в `docs/Planning/in-progress/`.

**Когда создаётся:**
- При запуске задачи (ещё до открытия worktree), если задача достаточно сложна чтобы её описать.
- Агент создаёт файл `docs/Planning/in-progress/<slug>.md` с описанием: что делать, какие файлы менять, паттерны тестов.

**Когда удаляется:**
- В шаге 19 фазы 3 — одновременно с удалением worktree и ветки, _после_ одобрения пользователем и merge в main.
- Файл удаляется в том же коммите, что завершает merge (или отдельным коммитом прямо в main сразу после merge).
- До одобрения файл остаётся — он часть артефакта для ревью.

**Сводный tracking-документ (`obstacle_interaction_coverage.md` и аналоги):**
- Статус задачи в roadmap-таблице обновляется при merge: `📋 В очереди` → `✅ Выполнено`.
- Ссылка на `<slug>.md` остаётся в таблице даже после удаления файла — как ссылка на историю (файла нет, но история в git).

## Git

- Коммитить только файлы текущей задачи.
- Коммит + push после каждого завершённого логического шага. Не копить до конца задачи.
- Не делать force-push.
- При ошибке push — остановиться и сообщить точную ошибку.

## Отчёт по завершении задачи

Всегда указывать:
- Тип задачи: аналитическая или исполнительная.
- Оставшиеся блокеры или ручные проверки.

Для аналитической:
- Краткий итог находок.

Для исполнительной:
- Результат валидации и какие проверки запущены.
- Ветка и путь worktree.
- Хэш коммита.
- Успешность push.
- Подтверждение `Tech Done` и `Workflow Done`.
- Подтверждение `Promotion Check Done` (`promoted X / kept incubating Y`).
