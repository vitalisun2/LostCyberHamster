# Расследование багов и регрессов

Единый процесс для починки runtime-багов, gameplay-регрессов и тестовых провалов, когда корень проблемы не доказан заранее.

## Когда применять

- Пользователь сообщает о новом баге или регрессе.
- Автопрогон или ручной прогон показывает потерю жизни, неверное действие, ухудшение экономики или расхождение с описанием тестового уровня.
- Есть несколько возможных причин и риск начать подгонять симптомы.

## Главный принцип

Работать строго с одной проблемой за раз. Не брать в один цикл несколько регрессов, даже если они проявились в одном наборе тестов. Для каждого регресса заводить отдельный документ расследования и доводить его до корня проблемы, решения и проверки.

## Обязательный артефакт

Для каждого регресса создать отдельный файл в `docs/Planning/in-progress/`:

```text
docs/Planning/in-progress/<short-bug-slug>-analysis-<yyyy-mm-dd>.md
```

Документ должен содержать:

1. Scope: один конкретный регресс, уровень, скорость, ожидаемое и фактическое поведение.
2. Источники данных: логи, тестовый уровень, релевантные файлы кода и ассеты.
3. Гипотезы: каждая с критериями подтверждения и опровержения.
4. Факты по коду: только после чтения тел методов, констант и call path.
5. Факты по логам: точные события, время, кадры, состояние, выбранный план, результат.
6. Статус гипотез: подтверждена, опровергнута, требует данных.
7. Корень проблемы: только когда факты дают высокую уверенность.
8. Решение: архитектурное, без подгонки порогов под один кейс.
9. Проверка: какие уровни и скорости прогнаны, результат, остаточные риски.

## Цикл работы

1. Зафиксировать один регресс и создать документ расследования.
2. Сформулировать начальные гипотезы без вывода о корне проблемы.
3. Разделить сбор данных на независимые направления и сразу отправить субагентов на разумное максимальное число независимых задач. Разрешения пользователя на это не ждать: для расследования багов и регрессов распараллеливание сбора фактов — поведение по умолчанию.
4. Читать релевантный код полностью: вызывающие методы, вызываемые методы, константы, policy, validators, runtime callbacks.
5. Если логов не хватает, добавить только точечную диагностику для проверки конкретной гипотезы.
6. Удалить или отключить лишние шумные логи, если они тормозят прогон или мешают анализу.
7. Прогнать тест только для сбора недостающих данных или для проверки решения с высокой уверенностью.
8. Свести факты в документ и явно отметить, какие гипотезы подтверждены или опровергнуты.
9. Если уверенность в корне проблемы низкая, не реализовывать fix. Добрать данные, уточнить гипотезы, при необходимости снова подключить субагентов.
10. Реализовать решение только после того, как корень проблемы виден из кода и логов с высокой уверенностью.
11. Проверить проблемный уровень, затем релевантный regression set.
12. После успешной проверки убрать временные логи, сделать code review изменений и привести код в порядок без изменения поведения.
13. Если корень проблемы уже доказан и пользовательский вывод готов, а остались только завершающие ритуалы (откат временных логов, `diff/status` checks, self-review, Learning Review), делегировать их субагентам и не задерживать основной ответ, если результат этих проверок не может изменить вывод о корне проблемы.

## Требования к гипотезам

- Гипотеза должна иметь проверяемый признак в коде, логе или ассете.
- Для каждой гипотезы заранее указать, какой факт её опровергнет.
- Не оформлять предположение как вывод, пока не прочитан полный execution path.
- Если аргумент зависит от чисел, прочитать определения констант и записать значения в документ.

## Работа с логами

- Логи добавлять по месту и под конкретный вопрос.
- Для gameplay-регрессов предпочитать компактные события: frame, time, deltaTime, state, lane, action, trigger/completion, obstacle bounds, reason.
- Не оставлять временные логи после завершения расследования.
- Если логирование меняет производительность, сначала уменьшить шум, затем повторить прогон на `TimeScale=1`.

## Работа с субагентами

- По умолчанию использовать субагентов максимально эффективно: код, логи, ассеты, runtime-order, константы и тестовую инфраструктуру можно раздать разным агентам, если их scope не конфликтует.
- Если уже есть свободные простаивающие субагенты, переиспользовать их через follow-up, когда это быстрее и контекстно выгоднее. Создавать новых субагентов, когда новый чистый scope или дополнительный параллелизм эффективнее.
- Субагент получает узкий вопрос и свою секцию документа.
- Не давать двум субагентам один и тот же scope.
- Если после первого раунда уверенность в root cause низкая, запускать дополнительных субагентов на новые конкретные гипотезы или недостающие факты.
- Субагенты собирают факты, а финальный вывод о корне проблемы делает основной агент после сверки всех секций.
- Если данные противоречат друг другу, основной агент добирает raw evidence, а не выбирает удобную версию.
- После доказанного root cause основной агент не тратит критический путь на завершающие ритуалы: cleanup, финальные проверки и ретроспективу нужно делегировать свободным субагентам, если это не меняет доказанный вывод.

## Запреты

- Не чинить несколько регрессов в одном цикле.
- Не подбирать magic gap, threshold или extra guard без доказанного корня проблемы.
- Не запускать тесты сериями в надежде, что одна из правок поможет.
- Не использовать название метода или переменной как доказательство поведения.
- Не объявлять проблему решенной, пока временные логи не убраны и regression set не прошел.
