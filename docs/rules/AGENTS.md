# Правила для AI-агентов


## *** Обязательно к прочтению ***

### Работа с Git и Workspace

Workspace нужен для параллельной работы агентов: каждый агент изолированно меняет код и ассеты в своей задаче. Проверка Unity выполняется последовательно на общем прогретом стенде `integration/unity-live`, где уже есть зависимости и импортированные библиотеки. Это экономит время и не требует запускать отдельный Unity Editor для каждого workspace.

Порядок работы:

1. Агент создает именованный локальный workspace и отдельную ветку для задачи. Workspace используется только для изменений в коде и ассетах.
2. После завершения изменений агент проверяет, свободен ли стенд `integration/unity-live`. Занятый стенд помечен lock-файлом с задачей и статусом работы.
3. Если стенд свободен, агент создает lock-файл, переносит изменения из workspace на стенд и проверяет проект в Unity Editor: сборку, компиляцию и ошибки в консоли.
4. Если проверка успешна, агент сообщает о готовности и передает функционал пользователю на проверку.
5. После подтверждения пользователем агент коммитит и пушит изменения в ветку `integration/unity-live`.
6. Агент удаляет lock-файл, ветку и папку рабочего workspace.

Так несколько агентов работают параллельно, а проверка Unity последовательно проходит на общем стенде.

### Обязательный стиль общения

Это обязательное правило для каждого агента.

- В начале задачи агент включает локальный skill `caveman` в режиме `full` и использует его во всех ответах.
- Менять уровень Caveman или выключать его можно только по явному запросу пользователя.
- Отвечай только на поставленный вопрос: кратко, простым неформальным языком, без воды.
- Детали добавляй только когда они нужны для решения. Для перечислений используй маркеры.

### Обязательный стиль документации

Это обязательное правило для любой создаваемой или изменяемой документации.

- Пиши в режиме `caveman full`: кратко, просто, технически точно.
- Описывай утверждённое: что нужно и как это работает.
- Не включай негативные сценарии, отвергнутые варианты, ограничения вне текущего решения и фразы «не нужно / не добавлять / не делать».
- Исключение: негативный факт нужен, только если это реальный blocker, риск или явное решение пользователя.
