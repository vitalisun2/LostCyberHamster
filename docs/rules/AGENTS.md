# Правила для AI-агентов

Единая точка входа для всех AI-агентов в этом репозитории: Claude Code, Codex, GitHub Copilot.

Язык — русский. Английский — только по явному запросу.

## Как агенты получают этот файл

| Агент | Механизм |
|---|---|
| Codex | Читает `docs/rules/AGENTS.md` (настроить путь в конфигурации Codex) |
| Claude Code | Читает `CLAUDE.md`, который ссылается на `docs/rules/AGENTS.md` |
| GitHub Copilot | Читает `.github/copilot-instructions.md`, который ссылается на `docs/rules/AGENTS.md` |

## Что читать перед работой

Для любой задачи: прочитать запрос и релевантные исходники, ассеты, планы и инструменты.

Для исполнительной и существенной аналитической задачи — дополнительно:

1. `docs/rules/agent_efficiency_playbook.md` — накопленные lessons и правила более быстрой и точной работы агента
2. `docs/rules/architecting_and_coding_principles.md` — общие принципы архитектуры и кодирования
3. `docs/rules/code_conventions.md` — конвенции кода и валидация
4. `docs/rules/temporary_current_rules.md` — временные обязательные правила текущего этапа разработки
5. [if-relevant: бот, gameplay, тесты] `docs/rules/iteration_cycle.md` — итерационный цикл тестирования бота
6. [if-relevant: инструменты, автопрогон, логи] `docs/rules/agent_tools.md` — каталог инструментов проекта
7. [if-relevant: архитектура, ассеты, новые системы] `docs/architecture_knowledge_base.md` — архитектурные решения и паттерны (читать только релевантные секции)
8. [if-relevant: code review, self-review после доработки] `docs/rules/code_review_principles.md` — принципы ревью архитектурной целостности и ownership
9. [if-relevant: подготовка плана реализации, реализация, рефакторинг, code review] `docs/rules/clean_code_by_b_martin/README.md` — выбрать только релевантные темы Clean Code до подготовки плана и сверить их перед первой содержательной правкой; это вспомогательный слой, приоритет всегда у project rules
10. Активный план в `docs/Planning/in-progress/`, если задача привязана к плану
11. Релевантные исходники, editor tools, ассеты и тесты

## Профиль пользователя

- Единственный разработчик на проекте.
- Опыт: senior-уровень, глубокое понимание архитектуры, Unity, C#.
- Ожидает от агентов профессионального качества кода и архитектурных решений.

## Стиль общения

- Кратко, без воды, без эмодзи (если не просят).
- По умолчанию отвечать максимально кратко: короткий абзац или несколько коротких буллетов. Подробности, разборы и длинные объяснения давать только по явному запросу пользователя.
- Отвечать строго на заданный вопрос; не добавлять пояснения о том, о чем пользователь не спрашивал.
- Не заканчивать сообщение наводящим или предлагающим вопросом. Пользователь сам скажет, что делать дальше.

## Процесс выполнения задачи

1. Прочитать запрос. Изучить релевантный код, ассеты, планы и инструменты до начала правок. **Если пользователь выдвигает гипотезу или задаёт аналитический вопрос — сначала пройти по затрагиваемому коду и только после этого отвечать.** Без проверки по коду — не отвечать.
2. Определить тип задачи и ожидаемый результат.
3. Если релевантная рекомендация из `docs/rules/clean_code_by_b_martin/` существенно расходится с проектным правилом, следовать проектному правилу, но кратко сообщить пользователю о расхождении: что требует проект и какую альтернативу предлагает Clean Code.
4. Выполнить запрошенную работу в соответствии с явными инструкциями пользователя и текущим рабочим контекстом.
5. Провалидировать по `docs/rules/code_conventions.md`.
6. Если валидация не прошла и проблема связана с задачей — починить. Если не связана — остановиться и сообщить о блокере.
7. Learning Review по `agent_efficiency_playbook.md` (см. секцию «Ретроспектива и дообучение» ниже).
8. Сообщить результат и остановиться, ждать code review или следующей команды пользователя.

## Ретроспектива и дообучение

Выполняется после каждой аналитической или исполнительной задачи как последний рабочий шаг перед финальным ответом пользователю. Подтверждение пользователя не требуется.

1. **Efficiency Review (обязательно):** проанализировать собственную работу на скорость, точность, лишние шаги, неудачные попытки и расход токенов.
2. **Lesson Routing:** если найден новый полезный паттерн формата «ошибка/риск -> причина -> рабочий ход -> правило», дополнить `docs/rules/agent_efficiency_playbook.md`. Если lesson относится к коду, инструментам, бот-итерациям или архитектуре — перенести его в файл-владелец темы и оставить в playbook promoted-ссылку.
3. **No-empty rule:** если нового lesson нет, не добавлять пустую запись и кратко отметить это в финальном отчёте.
4. **Ревью правил:** быстро проверить затронутые `docs/rules/` на дубли, устаревшие правила и возможный рефакторинг структуры. Если есть что исправить — исправить в той же задаче.
5. **Promotion Check (обязательно):** проверить новые/обновлённые lessons на зрелость. Зрелые lessons не оставлять в incubating: переносить в файл-владелец и отмечать в playbook как promoted.

## Управление правилами

При добавлении нового правила:

1. Проверить все файлы в `docs/rules/` — нет ли уже такого или похожего.
2. Найти файл-владелец темы → добавить буллет или расширить существующую секцию.
3. Если тема новая и не вписывается ни в одну существующую секцию → оценить:
   - Тема является подтемой файла → добавить новую секцию в этот файл.
   - Тема самостоятельная и перегружает существующий файл → создать новый файл в `docs/rules/` с говорящим именем и добавить ссылку в секцию «Что читать перед работой».
4. Одна тема = один файл-владелец. Другие файлы могут только ссылаться, не пересказывать.
5. Формулировка — 1-2 строки на правило.
