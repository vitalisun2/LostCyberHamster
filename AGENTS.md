# Repository Workflow

Единый источник правды по рабочему процессу для всех AI-агентов в этом репозитории: Claude Code, Codex, GitHub Copilot.

Документ написан на русском — рабочий язык проекта. Общение с пользователем тоже на русском. Английский — только по явному запросу.

## Как агенты получают этот файл

| Агент | Механизм |
|---|---|
| Codex | Читает `AGENTS.md` автоматически |
| Claude Code | Читает `CLAUDE.md`, который ссылается на `AGENTS.md` |
| GitHub Copilot | Читает `.github/copilot-instructions.md`, который ссылается на `AGENTS.md` |

## Что читать перед работой

Перед началом задачи:

- Для любой задачи: прочитать запрос и релевантные исходники, ассеты, планы и инструменты, не гадать по устройству проекта.
- Для исполнительной задачи и для существенной аналитической задачи: дополнительно обязательно прочитать список ниже.

Обязательный список для исполнительных и существенных аналитических задач:

1. `docs/rules/ai_workflow_lessons.md` — накопленные уроки (обязательно каждую сессию)
2. `docs/architecture_knowledge_base.md` — архитектурные решения и паттерны
3. `docs/rules/agent_tools.md` — каталог инструментов проекта (automation bridge, log reader и т.д.)
4. `docs/rules/ai_workflow.md` — итерационный цикл реализации, тестирование, отчётность
5. Активный план в `docs/Planning/current/`, если задача привязана к плану
6. Релевантные исходники, editor tools, ассеты и тесты

Дополнительные конвенции по Unity/коду — в `.github/copilot-instructions.md`.

## Структура репозитория

## Ветки и worktree

### Когда нужен worktree

Есть только два типа задач:

- **Аналитические задачи**: анализ, исследование, аудит, ответы на вопросы, оркестрация background-агентов и создание вспомогательных артефактов анализа. Для них не создаются ветка и worktree. Если такие артефакты окажутся ценными, их дальнейший commit/merge выполняется только по явному отдельному решению пользователя.
- **Исполнительные задачи**: любые изменения кода, ассетов, настроек, тестов, документации или других файлов репозитория как части результата задачи. Такие задачи всегда выполняются в отдельном worktree со своей веткой.

### Именование веток

Единый префикс для всех агентов: `task/<slug>`.

Примеры: `task/fix-switchlane-safety`, `task/add-levelkey-struct`, `task/cleanup-roofrun`.

Не использовать префиксы, привязанные к агенту (`codex/`, `claude/`, `copilot/`).

### Размещение worktree

Все worktree создаются в `.worktrees/<slug>`. Эта директория в `.gitignore`.

### Жизненный цикл задачи

```
Исполнительная задача:
1. Создать worktree + ветку task/<slug>
2. Реализовать изменения внутри worktree
3. Провалидировать (компиляция, тесты, автопрогон — по типу изменений)
4. Смержить в main (по одной задаче за раз, последовательно)
5. Удалить worktree, локальную ветку и remote-ветку
```

После merge между задачами остаётся только основной каталог (корень репозитория).

## Процесс выполнения задачи

1. Прочитать запрос. Изучить релевантный код, ассеты, планы и инструменты до начала правок.
2. Определить тип задачи: аналитическая или исполнительная.
3. Для аналитической задачи: выполнить анализ, при необходимости создать локальные артефакты анализа без ветки и worktree, подготовить выводы для пользователя.
4. Для исполнительной задачи: создать worktree и ветку, затем реализовать минимальное полное изменение, соответствующее паттернам проекта.
5. Если исполнительное изменение затрагивает gameplay, бота, прогрессию, загрузку, сохранение, Addressables, UI или editor tooling — добавить или обновить необходимые тесты или валидационные ассеты.
6. Для исполнительной задачи провалидировать изменённые файлы (см. секцию «Валидация»).
7. Если валидация исполнительной задачи не прошла и проблема связана с задачей — починить. Если не связана или починить безопасно нельзя — остановиться и сообщить о блокере. Не коммитить сломанный код.
8. Для исполнительной задачи закоммитить, запушить, смержить в main, удалить worktree и ветку (см. «Жизненный цикл задачи»).
9. После завершения задачи сделать короткую ретроспективу. Если в процессе появился устойчивый полезный вывод для будущих задач — добавить его в `docs/rules/ai_workflow_lessons.md`.

## Параллельное выполнение

### Принцип

Параллельность по умолчанию: параллелить, если нет причин не параллелить.

### Когда НЕ распараллеливать

- Задача мелкая или линейная (один файл, одна тема).
- Подзадачи меняют одни и те же файлы — сериализовать.
- Координация дороже выигрыша по времени.

### Оркестратор

Для сложных задач основной агент (оркестратор):

1. **Декомпозирует** задачу на независимые подзадачи.
2. **Разделяет** по риску конфликтов: каждая подзадача — свой набор файлов.
3. **Раздаёт** подзадачи background-агентам. Каждому — чёткий scope, вопрос, формат результата.
4. **Собирает** результаты по завершении.
5. **Синтезирует** итоговый результат для пользователя.

### Параллельный анализ

Для глубокого исследования, поиска багов, аудита кодовой базы:

1. Оркестратор определяет области для анализа.
2. Формулирует подзадачи: какие файлы/классы/подсистемы изучить, на какой вопрос ответить.
3. Запускает background-агентов параллельно — каждый анализирует свой срез.
4. Агенты возвращают находки оркестратору. При необходимости они могут подготовить локальные артефакты анализа без создания ветки и worktree.
5. Оркестратор сводит всё в единый отчёт, разрешая противоречия.

Пример декомпозиции для расследования бага:

```
Оркестратор: "SwitchLane ломается на паттерне X"
  → Агент 1: ActionGenerator — как формируются кандидаты SwitchLane
  → Агент 2: StateProjector — как оценивается безопасность
  → Агент 3: StepExecutor — как действие выполняется в runtime
  → Агент 4: TapMechanics + CollisionController — как SwitchLane работает в game engine
Оркестратор: синтез находок → корневая причина
```

### Параллельная реализация (worktree на каждую подзадачу)

Для крупных задач с независимыми подсистемами:

1. Оркестратор создаёт worktree + ветку для каждой подзадачи.
2. Каждый агент работает в своём worktree.
3. Агенты валидируют изменения независимо.
4. Оркестратор мержит завершённые подзадачи в main последовательно, по одной.
5. После каждого merge — удаление worktree и ветки.

Пока одна подзадача ревьюится или мержится — следующая безопасная подзадача уже может стартовать.

## Unity: правила владения файлами

Unity YAML-ассеты (сцены, префабы, ScriptableObject) практически не мержатся. Один владелец на файл.

Высококонфликтные пути — всегда один владелец:
- `LostCyberHamster/Assets/AddressableAssetsData/`
- `LostCyberHamster/ProjectSettings/`
- `LostCyberHamster/Packages/manifest.json`, `packages-lock.json`
- `*.unity`, `*.prefab`, `*.asset`, `*.meta`

Рекомендуемое разделение по подсистемам:
- Gameplay/runtime: `Assets/Scripts/`
- Editor tooling: `Assets/Editor/`
- UI: `Assets/Scripts/UI/`
- Контент и уровни: `Assets/Content/`
- Документация: `docs/`

Если задача требует согласованных изменений в коде и контенте — вести её в одном потоке, не разделять.

## Валидация

- C# скрипты: как минимум проверка компиляции.
- Gameplay, бот, тестовые уровни: итерационный цикл из `docs/rules/ai_workflow.md` (automation bridge, анализ логов).
- EditMode/PlayMode: запуск Unity-тестов, если они есть.
- Addressables, build config: sync/build валидация, если доступна.
- Не изобретать тяжёлую инфраструктуру в рамках текущей задачи, если пользователь не просил.
- Не считать задачу выполненной, если валидация не пройдена.

## Git

- Коммитить только файлы текущей задачи. Не коммитить чужие изменения, уже присутствовавшие в worktree.
- Не делать force-push.
- При ошибке push (аутентификация, права, защита ветки, расхождение с remote) — остановиться и сообщить точную ошибку.

## Стиль общения

- Русский язык. Английский — только по явному запросу.
- Кратко, без воды, без эмодзи (если не просят).

## Отчёт по завершении задачи

Всегда указывать:
- Тип задачи: аналитическая или исполнительная.
- Оставшиеся блокеры или ручные проверки.

Для аналитической задачи:
- Краткий итог находок.
- Какие артефакты анализа были созданы локально, если они создавались.

Для исполнительной задачи:
- Результат валидации и какие проверки были запущены.
- Ветка и путь worktree.
- Хэш коммита.
- Успешность push.
