# Снимки Unity UI

Зависимость: соседний скилл [image-gallery](../image-gallery/SKILL.md). Он владеет единственным HTML-шаблоном и сборщиком; `capture` вызывает его автоматически.

Результат: оригинальные PNG и готовая HTML-галерея с группировкой по смыслу и состояниям. По умолчанию только запрошенный игровой UI; DEV и дизайн-разбор включать по отдельному запросу.

## От запроса к кадрам

1. По коду установить цепочку: feature/flow → навигация → маршрут/идентификатор экрана → controller/presenter → prefab/Canvas или UXML/USS → условия отображения. Искать через `rg`. Читать конкретные обработчики и ветви отображения. Слова пользователя — отправная точка, а не готовый список экранов.
2. Составить короткий план: кейс, состояние, источник в коде, способ подготовки, видимый контрольный элемент/текст. Для flow сохранить порядок экранов. Брать основные визуально различные состояния; одинаковый вид при разных числах объединять. Служебные экраны и несвязанные фичи не расширяют scope.
3. Найти существующий адаптер съёмки в проекте. Выбрать только нужные состояния. Если адаптера нет, прочитать [контракт](references/capture.md) и написать подготовку поверх реальных API проекта; захват реализован здесь, сайт собирает соседний [image-gallery](../image-gallery/SKILL.md). Для простого снимка текущего UI Toolkit доступен [готовый адаптер](assets/current-screen-adapter.cs.txt).
4. Сохранить план вне Assets, например `.temp/ui-gallery/<имя>/plan.json`. Все состояния имеют `expected` с именем реального видимого UI-элемента. Для меняющегося текста добавить `expectedText`. Числа/даты — явные примеры в `data`.

## Запуск

Команды из корня репозитория; Python 3 и `unity` доступны в PATH:

```powershell
python .agents/skills/unity-ui-capture/scripts/capture.py capture --project <путь-к-Unity-проекту> --adapter <адаптер.cs> --plan <план.json> --out <новая-папка-результата>
```

Инструмент проверяет Editor и lock, запускает собственную Play-сессию, вызывает адаптер, снимает кадры, вызывает восстановление, останавливает Play Mode и собирает галерею. Создание тестовых данных, способ открытия экранов и восстановление исходного состояния принадлежат адаптеру проекта. Запуск требует чистых сцен и остановленного Play Mode. Если проект использует общий integration lock, передать его через `--lock-file`. Занятой Editor/lock не перехватывать.

Выполнять Unity-команды последовательно. Если вызов инструмента вернул session ID, продолжить его ожидание; повторный capture не запускать. При ошибке читать `run.json` и `capture-result.json`: инструмент сохраняет успешные кадры и ошибки, неполный набор явно помечается.

## Проверка и выдача

- Открыть по одному кадру каждого нового типа UI, затем кадры с различающимися состояниями. Проверить наличие нужного содержимого, соответствие подписи, загрузку ассетов и отсутствие посторонней модалки. Автоматическая проверка bounds/текста помогает, но не заменяет просмотр.
- Ошибочный кадр переснять только нужным fixture; сайт повторно собирать готовой командой `build`. Не рисовать имитации экранов и не переписывать HTML.
- Способ подготовки подписать честно: реальные контроллеры с моковыми моделями; визуальные overrides; статичный фон вместо игрового мира. Прямой вызов окна не подтверждает переходы user flow. Уведомления для оценки размещения показывать через штатный host с его ограничениями.
- Дать ссылку на `index.html`, число кейсов/кадров и реальные ограничения. Если нужен браузер, запустить готовый `serve` и открыть URL через `open_in_codex`. Готовая галерея работает и напрямую как локальный HTML, без сервера.

## Перенос

Обе соседние папки `.agents/skills/unity-ui-capture` и `.agents/skills/image-gallery` хранятся в Git и переносятся вместе для полного цикла. `image-gallery` также работает самостоятельно. Требуются Unity-проект, Python 3, Unity Editor, настроенный Unity CLI/Pipeline и Newtonsoft.Json (Unity package) для обмена данными. Пути определяются относительно проекта и папки скилла; локальные токены и пользовательские сохранения в скилл не входят.
